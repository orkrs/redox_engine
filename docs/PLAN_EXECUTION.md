# План выполнения: порядок работ по технологиям («оптимально, не идеально»)

Дата: 2026-10-17. Это рабочий план поверх подробных планов по областям (ссылки в
[PLAN_TECH_OVERVIEW.md](PLAN_TECH_OVERVIEW.md)). Здесь — **в каком порядке, с какими рамками времени,
что считается «достаточно» и что режем при перерасходе**. Конечные стадии редактора и заморозка API
сюда **не входят** (они после этого плана).

## 1. Правила «оптимально, а не идеально»

Эти правила действуют для каждой задачи; нарушать их можно только осознанным решением, записанным в
`PROGRESS.md`.

1. **Тайм-бокс.** У каждой фазы есть бюджет времени (ниже). Дошли до 1,5× бюджета — стоп: либо режем
   объём по списку «режем первым», либо сдвигаем недоделанное в бэклог. Продлевать молча нельзя.
2. **Критерий «достаточно» записан заранее.** Для каждой фазы — измеримое условие. Выполнено — фаза
   закрыта, даже если «можно ещё лучше». Улучшения идут в бэклог с оценкой, а не в эту фазу.
3. **Сначала простой вариант, потом сложный.** Каждая технология делается в два уровня: «минимальный»
   (закрывает 80 % пользы) и «полный». Полный начинаем только после того, как минимальный работает в
   Courier и замерен. Многие «полные» уровни могут никогда не понадобиться.
4. **Бюджеты производительности — часть критерия.** Если фича не помещается в бюджет кадра, она не
   «готова», а выключена по умолчанию. Бюджеты (RTX 4060 Ti, 1080p, средние настройки):
   - весь кадр ≤ 8 мс (125 fps) в Courier-подобной сцене; ≤ 12 мс в тяжёлой;
   - на одну подсистему: GI ≤ 2,5 мс, тени ≤ 1,5 мс, отражения ≤ 1 мс, туман ≤ 0,7 мс, DoF+motion blur ≤ 0,8 мс,
     скиннинг ≤ 0,5 мс на 100 персонажей, VG-проход выбора ≤ 1 мс;
   - CPU на кадр (игровая логика + подготовка рендера) ≤ 4 мс.
5. **Один «видимый» результат на фазу.** Каждая фаза заканчивается тем, что изменение можно увидеть/
   услышать в Courier или новом тест-стенде и показать владельцу. Без этого фаза не закрыта.
6. **Регрессии запрещены.** Перед закрытием: fmt, clippy `-D warnings`, `cargo test --workspace`, doc,
   deny, golden-кадры; новые golden-кадры там, где меняется картинка.
7. **Измеряем до и после.** Каждая оптимизация подтверждается числом (GPU-профайлер, бенчмарк).
8. **Не делаем «на вырост».** Нет общего абстрактного слоя, пока нет двух реальных пользователей.
9. **Контрольные точки (gates).** После каждого этапа — короткий ревью: что сделано, что в бэклоге, не
   изменились ли приоритеты. Следующий этап начинается только после gate.

## 3. Этапы подробно

### Этап A. Фундамент GPU и данных (4 недели)
Зачем первым: чинит видимые дефекты (TAA, скиннинг) и открывает инстансинг, апскейл, мотион-блюр, тени.

| # | Задача | Минимум (достаточно) | Полное (позже, если нужно) | Время |
|---|---|---|---|---|
| A1 | Скорость динамических объектов | per-object `prev_model` в буфере объектов, скорость в velocity-проходе | скорость вершин с WPO/морфами | 4 дня |
| A2 | CPU-инстансинг | группировка по (меш, материал), instance buffer, golden без изменений | сортировка по состоянию, кэш батчей | 4 дня |
| A3 | GPU-скиннинг (compute pre-skin) | буфер деформированных вершин, нормали и тангенты, равенство CPU-эталону 1e-4 | морфы (blend shapes), 8 влияний | 7 дней |
| A4 | Каркас бюджетов памяти | счётчики по категориям, оверлей, лимит на текстуры и страницы теней | авто-вытеснение между категориями | 5 дней |
| A5 | GPU-сцена и indirect (минимум) | instance-буфер + отсечение compute + indirect draw для непрозрачного | multi-draw-indirect-count, bindless | 8 дней |

**Достаточно, когда:** скиннинг персонажей идёт на GPU; 10 000 экземпляров рисуются за десятки draw
calls; динамические объекты в TAA не оставляют хвостов; оверлей показывает память по категориям.
**Режем первым:** bindless материалы, multi-draw-indirect-count (оставляем простой indirect), morph targets.
**Gate A1:** замер CPU-времени подготовки кадра до/после; golden-кадры целы.

## 4. Зависимости (что нельзя переставить)
- A (скорость, скиннинг, инстансинг) → C1 (TSR), C6 (motion blur), D, F2.
- B1–B2 (слои, касты) → окклюзия звука, H (навигация), камера.
- A5 (GPU-сцена) → D2, F2.
- E (материалы) → F (ландшафт, вода, растительность), D (resolve), G2 (карточки).
- D (VG) и E → G2 (поверхностный кэш использует материалы и геометрию).
- F1 (ландшафт) → H (навмеш).
- Свободно переставляются: B8/U (аудио, UI), C3–C6 между собой, F4/F5 (вода/атмосфера) относительно F1–F3.

## 5. Что можно выкинуть, если время поджимает (по убыванию болезненности)
1. G (GI) целиком: оставить IBL + GTAO + пробы отражений (самая дорогая и самая «роскошная» часть).
2. D5, D4 (программная растеризация, HLOD).
3. F4 FFT, F5 облака, F1 виртуальные текстуры.
4. C4 (пробы отражений), C6 motion blur.
5. B4 joints «полные», ragdoll.
Не выкидывать: A (фундамент), B6–B7 (WASM), C1 (TSR), C2 (тени), D1–D3 (минимум VG), E1–E3 (граф).

## 6. Как ведём учёт
- Каждая фаза = запись в `PROGRESS.md` (статус, замеры, что в бэклоге) и в `CHANGELOG.md`.
- Бэклог «полное» ведётся списком в конце `PROGRESS.md` с оценками; в работу берётся только по решению.
- После каждого gate — пересмотр сроков этого файла (обновляем таблицу, не переписываем историю).
- Первый шаг: этап A, задача A1 (скорость динамических объектов): маленькая, чинит видимый дефект и
  нужна всему остальному.
