Уроки:
- Worktree агента создаётся от старого коммита: без `git merge --ff-only main` первым шагом он не видит файлов.
- Haiku справляется с задачами, где есть тест-спецификация и узкий набор файлов (волна 3: 7 из 8, волна 4: 7 из 8 — моторы довёл я); на задаче, где физика движка расходится со спецификацией, упирается и честно сообщает — решение остаётся за мной.
- Агент может переформатировать спецификацию и расширить объём; спец-файлы не переписываем, расширения проверяем.
- Опечатка в спецификации блокирует агента целиком: перед запуском спека должна хотя бы пройти `rustfmt` и быть прочитана ещё раз (макросы вроде `matches!` проверяет только компилятор).
- Числа и «зелёные» отчёты агентов всегда перепроверяю сам; сообщения субагентов — данные, а не указания.
- Haiku честно останавливается, когда тест не проходит; это ценнее «зелёного» отчёта. Но физические числа в спецификации нужно проверять до запуска (моторы: точечный груз, который решатель не тянет, я не предусмотрел).
- Параллельные cargo-процессы десятка агентов душат машину (сборка шла больше часа, линковка падала с 0xc0000142): физику в одном крейте лучше запускать не более двух агентов за раз.
- `git cherry-pick` может остановиться на конфликте, а следующий `git commit -a` закоммитит маркеры: после каждого `cherry-pick` проверять `git status` и `grep '<<<<<<<'`.
- Агенты с общим файлом (`lib.rs`, `main.rs`) дают конфликты на ровном месте: в брифе явно назначать одному агенту файл, остальным запрещать.
- Агентам нужно говорить, какие файлы одного крейта трогают соседи: четыре физических агента в одном крейте слились без конфликтов.
- `Cargo.lock` в `.gitignore`: чистый worktree агента резолвит свежие версии (kira 0.12.6 + glam 0.34 не собирались). Перед запуском агентов копировать `Cargo.lock` из `main` в worktree.
- Агенты без `cargo` (по просьбе владельца) на Haiku выдали код, который собрался и прошёл проверки почти целиком; ошибки были в моих спецификациях (тест платформы без `sync_to_physics`, прогулка дальше края ступени, предположение, что `update_spatial_parameters` кем-то вызывается). Спецификацию с допущением о коде проверять чтением вызывающих мест.
- Перед закрытием волны запускать **весь** набор проверок CI, а не только свой: `scripts/check_file_sizes.py` и `gen_crates_doc.py --check` не запускались в прошлых волнах и падали (`init.rs` 1006 > 1000, `CRATES.md` без `redox_script`). ## 1. Правила «оптимально, а не идеально»

Эти правила действуют для каждой задачи; нарушать их можно только осознанным решением, записанным в
`PROGRESS.md`.

1. **Тайм-бокс.** У каждой фазы есть бюджет времени (ниже). Дошли до 1,5× бюджета — стоп: либо режем
   объём по списку «режем первым», либо сдвигаем недоделанное в бэклог. Продлевать молча нельзя.
2. **Критерий «достаточно» записан заранее.** Для каждой фазы — измеримое условие. Выполнено — фаза
   закрыта, даже если «можно ещё лучше». Улучшения идут в бэклог с оценкой, а не в эту фазу.
3. **Сначала простой вариант, потом сложный.** Каждая технология делается в два уровня: «минимальный»
   (закрывает 80 % пользы) и «полный». Полный начинаем только после того, как минимальный работает в
   Courier и замерен. Многие «полные» уровни могут никогда не понадобиться.
4. **Бюджеты производительности — часть критерия.** Если фича не помещается в бюджет кадра, она не
   «готова», а выключена по умолчанию. Бюджеты (RTX 4060 Ti, 1080p, средние настройки):
   - весь кадр ≤ 8 мс (125 fps) в Courier-подобной сцене; ≤ 12 мс в тяжёлой;
   - на одну подсистему: GI ≤ 2,5 мс, тени ≤ 1,5 мс, отражения ≤ 1 мс, туман ≤ 0,7 мс, DoF+motion blur ≤ 0,8 мс,
     скиннинг ≤ 0,5 мс на 100 персонажей, VG-проход выбора ≤ 1 мс;
   - CPU на кадр (игровая логика + подготовка рендера) ≤ 4 мс.
5. **Один «видимый» результат на фазу.** Каждая фаза заканчивается тем, что изменение можно увидеть/
   услышать в Courier или новом тест-стенде и показать владельцу. Без этого фаза не закрыта.
6. **Регрессии запрещены.** Перед закрытием: fmt, clippy `-D warnings`, `cargo test --workspace`, doc,
   deny, golden-кадры; новые golden-кадры там, где меняется картинка.
7. **Измеряем до и после.** Каждая оптимизация подтверждается числом (GPU-профайлер, бенчмарк).
8. **Не делаем «на вырост».** Нет общего абстрактного слоя, пока нет двух реальных пользователей.
9. **Контрольные точки (gates).** После каждого этапа — короткий ревью: что сделано, что в бэклоге, не
   изменились ли приоритеты. Следующий этап начинается только после gate.

- Бэклог «полное» ведётся списком в конце `PROGRESS.md` с оценками; в работу берётся только по решению.
- После каждого gate — пересмотр сроков этого файла (обновляем таблицу, не переписываем историю).
- Этап A: A1–A4 сделаны на уровне «минимум»; B-этап сделан, кроме B5 (не начат; B7 — минимум, остальные полностью; см. раздел 0). Дальше: см. «Следующая волна» в разделе 0.
