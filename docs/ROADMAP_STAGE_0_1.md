# ЧАСТЬ A. Остаток этапа 0

Цель: репозиторий, которому можно доверять при рефакторингах этапа 1: зелёный CI на реальном

## A1. Проверить и довести CI (1–2 дня)

1. Запушить ветку и посмотреть первый реальный прогон (`windows-latest`; `ubuntu-latest` нужен только для `cargo-deny`, остальные проверки — Windows).
2. Починить то, что окажется красным. Ожидаемые проблемы:
   - `cargo test --workspace` на раннере без GPU: тесты, создающие wgpu-устройство, должны либо
     пропускаться (`#[ignore]` + явный запуск), либо использовать software-адаптер. Сейчас часть
     тестов помечена как ignored; составить список и убедиться, что их причина — именно GPU.
   - `cargo-deny`: первый запуск почти наверняка укажет лицензии вне списка (`MPL-2.0`, `Zlib`,
     `Unicode-3.0` и т. п.) и дубликаты версий. Решение: расширить `allow` осознанно, дубликаты
     оставить `warn`.
3. Проверить MSRV: установить заявленный `rust-version` и выполнить `cargo check --workspace`.
   Edition 2024 требует Rust 1.85+, это нижняя граница; если соберётся только на более новой —
   поднять значение. Добавить CI-задачу `msrv` (`dtolnay/rust-toolchain@<версия>` + `cargo check`).
4. Добавить `cargo audit` (отдельная задача по расписанию раз в неделю + на PR при изменении
   `Cargo.lock`).
5. Кэш: `Swatinem/rust-cache` уже подключён; проверить, что время холодной сборки укладывается
   в разумное (цель — меньше 15 минут, иначе вынести тяжёлые крейты).
6. Добавить `.github/dependabot.yml` (cargo + github-actions, раз в неделю, группировка
   минорных обновлений).
7. Добавить защиту ветки `main`: обязательные проверки `check`, `deny`; запрет прямого push
   (настройка репозитория, не файл).

DoD: последний коммит `main` зелёный на Windows; бейдж CI в README.

## 1.5 Сохранения и ввод (2–3 недели)

### 1.5.1. Сериализация мира (1–1,5 недели)
1. Формат: RON для читаемых сцен (разработка), бинарный (bincode/postcard) для сохранений и cooked-сцен;
   версия схемы в заголовке.
2. Основа: `Reflect` (1.3.5) + реестр типов с именами и стабильными идентификаторами типов (не `TypeId`).
3. Что сохраняется: сущности, компоненты, иерархия (родитель/дети), ссылки на ассеты (по GUID, 1.4.1), ссылки на
   другие сущности (переназначение id при загрузке).
4. Исключения: `#[reflect(skip)]`, компоненты рантайма (GPU-ручки, физические ручки — пересоздаются синхронизацией).
5. Миграции: функция `migrate(version_from, version_to)` на тип/глобально; тест на загрузку «старого» файла.
6. Интеграция: `WorldSession` редактора использует новый формат, а не ad-hoc (`--world` CLI).

## 1.6 Кроссплатформенность — ОТЛОЖЕНО (решение владельца: пока только Windows)

Linux, macOS, веб и мобильные не делаем до отдельного решения. Чтобы не закрывать себе дорогу, на этапе 1
соблюдаем дешёвые правила:
1. Пути только через `PathBuf`/`Path::join`, без ручных `\`; имена файлов регистрозависимы (писать как на диске).
2. Платформенный код (окно, время, пользовательские каталоги) держать в одном месте, а не размазывать по крейтам.
3. Не добавлять новых зависимостей, жёстко привязанных к Windows (`winapi`, `windows-sys`) без обёртки за трейтом.
4. Требования к GPU (features/limits) фиксировать в одной таблице при обновлении wgpu (1.1d), чтобы к порту вернуться с готовым списком.
5. Тир-система качества и порт Linux/macOS/веб остаются в бэклоге; прежний детальный план сохранён в истории git (коммит `551d28a`).

## Реестр рисков

| Риск | Вероятность | Влияние | Что делать |
|---|---|---|---|
| Обновление wgpu ломает VSM/профайлер/лимиты | высокая | высокое | идти по одной мажорной версии, golden после каждой, ветка отдельно |
