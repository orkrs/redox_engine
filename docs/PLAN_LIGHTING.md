# План: освещение и постобработка (GI, тени, отражения, туман, DoF, motion blur, апскейл)

Общий контекст: [PLAN_TECH_OVERVIEW.md](PLAN_TECH_OVERVIEW.md). Код: `crates/redox_render/src/gi`
(`ddgi.rs`, `ddgi_gpu.rs`), `sdf/` (запечённые SDF-атласы), `shadow/` (VSM, клипмап, кэш страниц),
`post/` (bloom, GTAO, tone mapping), `pass/taa.rs`, шейдеры `ddgi_trace.wgsl`, `vsm_*.wgsl`, `taa.wgsl`, `gtao*.wgsl`.

## 0. Что есть и что нет (по коду на 2026-10-17)

Есть: прямой свет (кластерное освещение), VSM-тени (клипмап, кэш страниц, временная фильтрация), GTAO,
bloom, SMAA, TAA с «камерной» скоростью, IBL из HDR/KTX2, DDGI-заливка проб (но по AABB сцены и модели
неба/солнца, без отражённого света), запечённые SDF-кирпичи.

**Нет** (уточнение к вопросу про SSR): SSR, отражений от проб (только глобальный IBL), объёмного
тумана, DoF, motion blur, скорости **динамических объектов** (поэтому TAA их размывает и «тянет хвосты»),
настоящего многоотражённого GI.

## 1. Глобальное освещение (аналог Lumen)

### 1.1 Что такое «аналог Lumen» и насколько мы его повторим
Lumen состоит из блоков: (1) **поверхностный кэш** (карточки: упрощённые снимки материала и света
поверхностей), (2) **трассировка** лучей по SDF (программно) или аппаратная (HWRT), (3) **финальный сбор**
через экранные пробы, (4) **кэш излучения** в мире для далёкого/вторичного света, (5) шумоподавление во
времени и пространстве. Вы правы: SDF + Surfel/Radiance Cache + желательно HWRT — это его ядро.
Мы сделаем **упрощённую версию** с тем же устройством, не клон: у Epic это годы работы команды.

### 1.2 Этапы (каждый даёт видимый результат и может жить отдельно)
| Этап | Что | Результат | Оценка |
|---|---|---|---|
| G1 | **DDGI по реальной сцене**: пробы бросают лучи в **глобальное SDF** (склейка запечённых мешевых SDF; уже есть `sdf/atlas.rs`, `gpu_atlas.rs`), в точке попадания берётся простой свет (прямое от солнца/точечных + эмиссия + предыдущий кадр GI для многократных отражений); хранение в октаэдрических текстурах освещённости и видимости, гистерезис; каскады сетки вокруг камеры (clipmap) | Свет «отскакивает»: красная стена подкрашивает соседние поверхности, тёмные комнаты освещаются | 3–4 недели |
| G2 | **Поверхностный кэш (cards)**: по 6 карточек на меш (ортографические снимки albedo/normal/emissive в атлас), каждый кадр освещаются прямым светом с тенями; точка попадания луча читает освещённость карточки | Цвет и свет в точках попадания правильные, многократные отражения | 3 недели |
| G3 | **Экранные пробы и финальный сбор**: пробы по тайлам 16×16 пикселей (адаптивно), экранная трассировка по Hi-Z для контактных деталей, фильтрация в пространстве и времени | Резкий локальный GI, контактные тени от света | 3 недели |
| G4 | **Отражения из того же кэша**: шероховатые отражения из проб/карточек, острые — SSR + (позже) HWRT | Единая система света и отражений | 2 недели |
| G5 | **Аппаратная трассировка (опционально)**: BLAS на меш, TLAS на кадр, ray query в compute для проб и отражений; SDF остаётся запасным путём | Точный GI и отражения на поддерживающих GPU | 3 недели + проверка |

**Про HWRT в wgpu.** В wgpu есть экспериментальная поддержка ray query / acceleration structure
(Vulkan, DX12). Перед G5 обязательно проверить, что нужные возможности доступны в используемой версии, а
как запасной путь держать SDF. Если поддержка нестабильна — G5 откладывается без ущерба остальному.

**Динамические объекты.** Для SDF динамика дорога (скинированные персонажи, двигающиеся объекты не
пересобирают SDF каждый кадр). Как у Lumen: персонажи не участвуют в SDF-трассировке, но видны в
экранных трассах; для крупных динамических объектов — упрощённые прокси (капсулы/сферы).

**Ограничения и бюджет.** Цель: GI ≤ 2,5 мс на 1080p на RTX 4060 Ti на среднем качестве; пробы и
кэши входят в бюджет памяти (PLAN_GEOMETRY.md, раздел 5). Уровни качества: Low (только IBL + GTAO),
Medium (G1), High (G1+G2+G3), Ultra (+G5).

**Тесты.** Эталонная «Cornell box»: красная и зелёная стены красят белую поверхность, яркость
сходится со значением эталонного трассировщика пути (CPU) с допуском; стабильность во времени (нет
мерцания: средняя разница соседних кадров); golden-кадры; бенчмарк GPU-таймером; тест утечек и
бюджета.

**Риски.** Шум и просачивание света через тонкие стены (leaking) — фильтр видимости (Chebyshev) и
смещение пробы; стоимость; сложность отладки (нужны режимы отладки: показать пробы, показать кэш).

## 2. Тени

### 2.1 Разделение статики и динамики в VSM
- **Сейчас.** Страницы теней кэшируются, но когда что-то движется (персонаж, дверь), затронутые страницы
  инвалидируются и перерисовываются целиком (`invalidate_shadow_region`). Анимированный меш инвалидирует
  свои страницы каждый кадр.
- **Решение.** Два слоя в одном пуле: **статические страницы** (рендерятся только при изменении
  статической геометрии или смещении клипмапа) и **динамические страницы** (в них каждый кадр пишут только
  динамические тени-кастеры; остальное не перерисовывается). Тест тени берёт минимум из двух слоёв.
- **Как.** Флаг `static/dynamic` на объекте (по умолчанию из компонентов: есть `RigidBody` динамика или
  `SkinnedMesh` → dynamic); в таблице страниц два бита-слоя; проход `vsm_depth` рисует статику в слой 0 и
  динамику в слой 1; `vsm_shadow_trace` сэмплирует оба.
- **Вы правы, что это нетрудно**: основной объём — аккуратное управление двумя слоями и инвалидация.
  Оценка 5–8 дней.
- **Тесты.** Двигающийся персонаж не вызывает перерисовку статических страниц (счётчик `pages_dirty` для
  слоя 0 равен 0); картинка совпадает с объединённым путём (golden); перемещение статического объекта
  инвалидирует нужные страницы.

### 2.2 Остальное по теням
- VSM для точечных и прожекторных ламп (кубическая/спот-версия), сейчас у точечных отдельные тени.
  Оценка 8–10 дней.
- Контактные тени (экранные, короткий луч по глубине) для мелких деталей: 3 дня.
- Мягкие тени с размером источника (PCSS-подобная фильтрация поверх VSM): 4–5 дней.
- Трассированные тени (опционально, вместе с HWRT).

## 3. Отражения

### 3.1 SSR
- Экранная трассировка отражённого луча по Hi-Z (уже есть Hi-Z), учёт шероховатости (конус → mip
  цвета предыдущего кадра), выход за край экрана и закрытые места → запасной вариант из проб/IBL,
  временная фильтрация.
- Тесты: зеркальный пол отражает объект; при выходе объекта из кадра плавный переход на пробы; без
  артефактов на краях. Оценка 5–6 дней.

### 3.2 Пробы отражений
- Компонент `ReflectionProbe { extent, capture_resolution, priority }`; захват кубической карты
  в движке (переиспользуем конвейер IBL: `IBLProcessor`, prefilter) или запекание в KTX2 (`redox_cook`);
  коробочная проекция (parallax correction), смешивание нескольких проб по влиянию, интерполяция.
- Цепочка: SSR → ближайшие пробы → глобальный IBL/небо (как вы и описали: связка SSR + Reflection Probes).
- Тесты: комната с пробой отражает свои стены с правильной параллакс-коррекцией; переключение проб без
  скачков. Оценка 6–8 дней.

## 4. Объёмный туман (froxel)

- **Вы правы: это froxel** — воксели в пирамиде видимости камеры (например, 160×90×64, глубина
  по экспоненте).
- **Проходы.** (1) заполнение плотности (высотный туман, локальные объёмы, частицы); (2) рассеяние света в
  каждом froxel от солнца (используем VSM-тени), точечных и прожекторных ламп (кластерные списки), с
  временным накоплением и джиттером; (3) интегрирование вдоль глубины (накопление пропускания и света);
  (4) применение в основном проходе/после: выборка по глубине пикселя.
- Лучи света (god rays) получаются автоматически из теней солнца.
- Тесты: однородный туман даёт известное по Бугеру-Ламберту затухание; сквозь отверстие в стене виден
  луч; без мерцания. Оценка 8–10 дней.

## 5. DoF и motion blur

- **DoF (глубина резкости).** Да, это «фокус на объектах»: то, что на фокусном расстоянии, резкое, ближе
  и дальше — размытое. **С виртуальной геометрией/Nanite это не связано**: DoF — независимая постобработка
  по буферу глубины. Алгоритм: радиус размытия (circle of confusion) из глубины и параметров камеры
  (фокусное расстояние, диафрагма, дистанция фокуса) → размытие диском с раздельной обработкой ближнего и
  дальнего планов (чтобы избежать просачивания). Режимы: кинематографический и мягкий игровой. Компонент
  `CameraLens`. Оценка 5–6 дней.
- **Motion blur.** Нужна **скорость каждого пикселя, включая динамические объекты** (сейчас её нет, см.
  раздел 6.1). Затем тайловая максимальная скорость и размытие по направлению движения, оценка 4–5 дней
  после готовой скорости.

## 6. Апскейл

### 6.1 Что сейчас не так с TAA и что значит «нормальный TSR»
- **TSR (Temporal Super Resolution)** — когда сцена рисуется в **меньшем** разрешении (например, 67 %),
  а временным накоплением джиттерных кадров восстанавливается полное разрешение. TAA сглаживает края
  при том же разрешении; TSR должен ещё и добавлять детали.
- Проблемы текущего TAA (по коду `taa.wgsl`, `velocity.wgsl`):
  1. **Нет скорости динамических объектов** — только камера (`prev_vp`): двигающиеся объекты размазываются
     или оставляют «хвосты», отсюда приходится сильно ограничивать накопление.
  2. Нет надёжной проверки валидности истории по глубине/нормали/ID объекта; отбраковка основана на
     цвете и глубине.
  3. Рассчитан на разрешение около 100 %; для сильного апскейла нужны джиттер под масштаб, апсэмплинг
     истории и сохранение резкости.
  4. Реактивная маска есть только для частиц; нужны маски для прозрачного и тонких деталей.
  5. Нет предэкспозиции и накопления в тонемаппированном пространстве для стабильной яркости.
- **План TSR.** (a) скорость динамических объектов (см. PLAN_GEOMETRY.md, GPU-скиннинг даёт позиции
  прошлого кадра); (b) история в разрешении вывода, валидация по глубине/нормали/ID; (c) джиттер и вес по
  масштабу; (d) резкость (RCAS уже есть) и анти-ринг; (e) маски реактивности. Оценка: 2–3 недели.

### 6.2 FSR, XeSS, DLSS
Ваша мысль почти верна, уточнение по открытости:
| Технология | Открытость | Что нужно |
|---|---|---|
| **FSR 2/3** (AMD) | открытый код (MIT), работает на любых GPU | можно портировать шейдеры на WGSL (законно по лицензии) — 2–3 недели; независим от производителя |
| **XeSS** (Intel) | бесплатный SDK, но **бинарный** (не открытый код), работает на любых GPU через DP4a, лучше на Intel | нужны нативные хэндлы Vulkan/DX12 → доступ к `wgpu-hal`; хрупко |
| **DLSS** (NVIDIA) | закрытый SDK, нужно соглашение с NVIDIA, только RTX | нативный Vulkan через `wgpu-hal`; хрупко |

Все три требуют **скорость динамических объектов** и **стабильный джиттер**, поэтому сначала пункт 6.1.
Предложение: **собственный TSR** (всё работает везде одинаково) → **порт FSR на WGSL** →
**DLSS/XeSS через `wgpu-hal` как опциональные плагины** (оценка 2 недели каждый с неопределённостью).
Общий трейт `Upscaler` с реализациями и переключателем качества.

## 7. Порядок
скорость динамических объектов (этап A) → TSR → статика/динамика теней → SSR → пробы отражений →
туман froxel → DoF/motion blur → G1 → G2 → G3 → G4 → порт FSR → G5 (опц.) → DLSS/XeSS (опц.).
Итого 3–5 месяцев чистой работы.
