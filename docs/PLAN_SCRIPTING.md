# План: скриптинг (Rust + WebAssembly)

Решение: [ADR 0005](adr/0005-scripting-wasm.md). Этот файл — подробный план. Общий контекст:
[PLAN_TECH_OVERVIEW.md](PLAN_TECH_OVERVIEW.md).

## 0. Ответ на вопрос «чистый Rust у нас будет или нет?»

**Будет, и он остаётся главным путём.** Слои:

| Слой | Язык | Для кого | Особенности |
|---|---|---|---|
| Движок | Rust | мы | крейты `redox_*` |
| Игровой код «нативно» | Rust | разработчик игры на Rust | системы ECS, плагины, максимальная скорость, полный доступ к API; собирается вместе с игрой |
| Игровой код «встроенный» | WASM (Rust, C/C++, Zig, AssemblyScript) | дизайнеры, моды, быстрые итерации | изолирован (песочница), горячая перезагрузка без пересборки движка, ограниченный API хоста |

Оговорка по WASM, чтобы ожидания были реалистичными:
- Скорость WASM обычно в 1,2–2 раза ниже нативного Rust для вычислений; главная цена — **вызов через
  границу хоста** (каждый обмен данными копирует байты). Поэтому API хоста делается «крупным»
  (пакетный доступ к компонентам), а не «вызов на каждое поле».
- WASM даёт больше возможностей по **языкам и безопасности** (песочница, моды), а не по скорости.
  Lua медленнее и динамичнее, но проще для дизайнеров; WASM требует тулчейн (компилятор).
- Если нужна максимальная скорость игровой логики — писать её на Rust нативно, WASM для остального.

## 1. Цели и не-цели

Цели:
- Загрузка `.wasm` модуля как ассета (из `.pak`), вызов `on_start`, `on_update(dt)`, `on_event`.
- Доступ к ECS через малое, пакетное, типобезопасное API.
- Песочница: лимит памяти, лимит времени (топливо/прерывание), никакого доступа к файлам и сети
  кроме как через хост.
- Горячая перезагрузка модуля при изменении файла с сохранением состояния игры.
- SDK для Rust (макросы, типы) и описание ABI для других языков.

Не цели (на первом этапе): компонентная модель WASM/WIT, отладчик с точками останова, скриптинг
рендера, многопоточность внутри модуля.

## 2. Выбор рантайма (решить прототипом, ADR 0006)

| Кандидат | Плюсы | Минусы |
|---|---|---|
| `wasmi` | чистый Rust, маленький, быстро собирается, интерпретатор, есть лимиты топлива | медленнее JIT в 5–20 раз |
| `wasmtime` | JIT (Cranelift), почти нативная скорость, зрелая песочница, прерывание по эпохам | тяжёлая зависимость, долгая сборка, больше кода |

План: сделать общий трейт `ScriptBackend` и реализовать оба на прототипе (1–2 дня), замерить стоимость
вызова хоста и вычислений, выбрать `wasmtime` для скорости, если стоимость сборки приемлема; `wasmi`
оставить как лёгкий запасной вариант за feature.

## 3. Архитектура

### 3.1 Крейт `redox_script` (новый)
- `ScriptRuntime` (ресурс ECS): загруженные модули, экземпляры, очередь событий.
- `ScriptModule` (ассет): байты `.wasm` + манифест (имя, версия API, запрошенные права).
- Компонент `Script { module: Handle<ScriptModule>, state: Vec<u8> }` на сущности (скрипт на сущность)
  и «глобальные» скрипты (ресурс).
- Система `run_scripts` в стадии `Update`: вызывает `on_update` у каждого экземпляра.

### 3.2 ABI (граница хоста), правила
- Только числа и указатели в линейной памяти модуля; строки как (ptr, len) UTF-8.
- **Пакетный доступ**: `query(component_mask) -> handle`, `read_batch(handle, out_ptr, cap) -> count`,
  `write_batch(handle, in_ptr, count)`. Компоненты в фиксированной бинарной раскладке (репр `C`),
  описаны в SDK; версия раскладки в манифесте.
- **Команды**: изменения структуры (spawn, despawn, add/remove) записываются в буфер команд модуля и
  применяются хостом после `on_update` (как `Commands` в ECS).
- **События**: хост кладёт события (столкновение, триггер, ввод) в кольцевой буфер, модуль читает.
- Хост-функции (первый набор): `log`, `time`, `input_axis/button`, `transform_get/set` (батч),
  `spawn_prefab`, `play_sound`, `raycast`, `overlap`, `emit_event`.
- Ошибки: хост возвращает код; паника модуля = trap → модуль отключается, ошибка в лог и в UI
  (игра не падает).

### 3.3 Песочница
- Лимит линейной памяти (по умолчанию 16 МиБ), лимит топлива/времени кадра (например, 2 мс на модуль),
  при превышении — прерывание и отключение с сообщением.
- Права в манифесте: `read_input`, `write_transform`, `spawn`, `audio`, `physics_query`; без права —
  функция не импортируется (линковка не пройдёт).

### 3.4 Горячая перезагрузка
- Наблюдение за файлом/ассетом; при изменении: сериализовать состояние (`Script.state`, которое модуль
  сам записывает через `save_state`), создать новый экземпляр, вызвать `on_load(state)`.
- Если ABI-версия не совпала — отказ с понятным сообщением, старый модуль продолжает работать.

### 3.5 SDK для Rust (`redox_script_sdk`, `no_std`-совместимый)
- Макрос `#[redox::script] fn update(ctx, dt)`, типы `Transform`, `Query<T>`, `Commands`.
- Шаблон проекта `cargo generate`-стиля: `cargo build --target wasm32-unknown-unknown`.
- Описание ABI для C/AssemblyScript (заголовки) — вторым этапом.

## 4. Фазы

| Фаза | Содержание | Критерий «готово» | Оценка |
|---|---|---|---|
| 1. Прототип | ScriptBackend, wasmi и wasmtime, модуль `on_update`, `log`, замер вызовов | отчёт: стоимость вызова хоста (нс), 10 000 вызовов за кадр; ADR 0006 | 2–3 дня |
| 2. Ядро | крейт `redox_script`, ассет `.wasm` из pak, система `run_scripts`, лимиты памяти и времени | модуль крутится в Courier; зацикленный модуль отключается без зависания | 4–5 дней |
| 3. API хоста v1 | транспорт ECS: query/read/write батчи, команды, события, ввод | модуль двигает 1000 сущностей; время кадра < 0,3 мс | 5–7 дней |
| 4. SDK Rust | макросы, шаблон, примеры (монеты Courier как модуль) | логика сбора монет Courier работает из WASM, тесты на хосте | 4–5 дней |
| 5. Горячая перезагрузка | наблюдатель, сохранение состояния, откат при ошибке | правка модуля меняет поведение без перезапуска игры | 3–4 дня |
| 6. Расширение API | физика (касты, overlap), звук, префабы, UI-события | модуль стреляет лучом, играет звук, открывает экран UI | 5–7 дней |
| 7. Другие языки | заголовки C, шаблон AssemblyScript | пример на втором языке | 3–4 дня |

## 5. Тесты
- Юнит: раскладка компонентов (бинарная совместимость), лимиты, права, ошибки ABI.
- Интеграционные: модуль с паникой, с бесконечным циклом, с выходом за память — игра жива.
- Бенчмарки: вызов хоста, чтение/запись батча 1k/10k, накладные расходы `run_scripts` на 100 модулей.
- Контрольный пример: поведение монет Courier идентично нативной версии (сравнение результата).

## 6. Риски
- Стоимость границы хоста съест выигрыш → пакетное API, измерять на фазе 1.
- Версионирование ABI → поле версии, отказ при несовпадении, тесты совместимости.
- Время сборки `wasmtime` → feature, кэш, при проблемах `wasmi` по умолчанию.
- Отладка модулей без отладчика → хорошие логи, `trap` с именем функции, режим трассировки вызовов.
