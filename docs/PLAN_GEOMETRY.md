# План: геометрия (виртуальная геометрия, HLOD, инстансинг, скиннинг, бюджеты памяти)

Общий контекст: [PLAN_TECH_OVERVIEW.md](PLAN_TECH_OVERVIEW.md). Код: `crates/redox_render/src/virtual_geometry`
(`meshlet.rs`, `lod.rs`, `culling.rs`, `gpu_cull.rs`, `hiz.rs`, `indirect.rs`, `cache.rs`, `asset_pipeline.rs`,
`runtime/`), шейдеры `vg*.wgsl`, `skinning.rs`, `cluster_gpu_cull.rs`.

## 0. Где мы и что уточнить в понимании

**Что уже есть в VG:** разбиение на meshlet'ы, несколько уровней LOD (`lod.rs`: каждый уровень — отдельный
набор meshlet'ов с упрощённой версией меша), GPU-отсечение (`vg_cull.wgsl`, Hi-Z), visibility buffer
(`vg_vis.wgsl`, `vg_resolve.wgsl`), индирект-отрисовка, асинхронная подготовка ассетов, теневой проход
(`vg_shadow.wgsl`).

**Чего нет до уровня Nanite:** иерархии кластеров (DAG) с бесшовным LOD на уровне кластера; стриминга;
программной растеризации мелких треугольников; единой «GPU-сцены» для всех видов геометрии.

**Про «Nanite производительнее».** Не всегда и не для всего:
- Выигрыш: плотная статическая геометрия (скалы, здания, скан-объекты), много треугольников — стоимость
  почти не зависит от числа треугольников, а зависит от числа пикселей.
- Не подходит или невыгодно: **скиннинговые** (деформируемые) меши, **alpha-test листва** и
  **прозрачные** материалы, **маленькие** меши (< ~1000 треугольников; накладные расходы больше выигрыша).
- Поэтому остаётся **гибридный конвейер**: VG для статического непрозрачного, классический путь с GPU-
  инстансингом для остального. Это нормальная практика (Unreal тоже так делает).

## 1. Виртуальная геометрия (аналог Nanite)

### 1.1 Иерархия кластеров (DAG) — основа
- **Идея.** Меш режется на кластеры по ~64–128 треугольников. Соседние кластеры группируются (4–8 штук),
  группа упрощается примерно вдвое с **заблокированной границей** (чтобы не было трещин), результат
  режется на новые кластеры; шаг повторяется до одного кластера. Получается DAG: у каждого кластера есть
  «ошибка упрощения» и ссылка на родителя.
- **Выбор LOD на GPU.** Кластер рисуется, если его ошибка в пикселях меньше порога, а ошибка родителя
  больше порога. Решение принимается **локально по каждому кластеру** без «прыжка LOD всего меша»,
  стыки между группами остаются закрытыми благодаря заблокированным границам и одинаковой ошибке группы.
- **Сборка (cook).** Расширить `asset_pipeline.rs` и `lod.rs`: `build_cluster_dag(mesh, params)`:
  1. meshlet'изация (есть, поставить границу 64–128 треугольников);
  2. группировка по смежности (граф кластеров, METIS-подобное разбиение или жадное по общим рёбрам);
  3. упрощение группы (quadric edge collapse, есть код для LOD; добавить блокировку границ группы);
  4. запись иерархии: `Cluster { bounds, lod_bounds_center_radius, error, parent_error, group_id, page }`.
- **Тесты.** Нет трещин (проверка границ групп), монотонность ошибки (ошибка родителя ≥ ошибки детей),
  число треугольников корневого уровня ≤ лимита, сборка детерминирована.
- **Оценка:** 8–12 дней (самая сложная часть).

### 1.2 Выбор кластеров и отсечение на GPU
- Вместо плоского прохода по всем meshlet'ам — обход иерархии: сначала отсечение **экземпляров** (instance
  culling: frustum + Hi-Z по ограничивающему объёму экземпляра), затем обход DAG волной (persistent
  threads или многопроходный compute: список «узлов к проверке» → список «кластеров к рисованию»).
- Отсечения: frustum, **Hi-Z occlusion по двум проходам** (кластеры, видимые в прошлом кадре, → Hi-Z → остальные), конус
  нормалей для обратных граней.
- Данные: структура `ClusterNode`, буферы очередей, счётчики; лимиты и переполнение (бюджет на кадр,
  при переполнении — огрубление LOD, а не пропажа геометрии).
- Тесты: сравнение с CPU-эталоном (какие кластеры выбраны) на тестовых мешах; GPU-тест без ошибок
  валидации; бенчмарк: 1 млн экземпляров × 100 кластеров, время прохода.
- Оценка: 6–8 дней.

### 1.3 Растеризация
- **Основной путь.** Аппаратная растеризация в visibility buffer (есть). Формат: (cluster_id, triangle_id)
  + глубина. Проверить достаточность 32 бит и при необходимости перейти на 64-битную запись.
- **Программная растеризация мелких треугольников (опционально, отдельная фаза).** Треугольники меньше
  ~4 пикселей аппаратная растеризация обрабатывает плохо; в compute рисуем их сами с атомарными операциями
  (`atomicMax` на 64-битное значение глубина+ID; в wgpu нужна фича `SHADER_INT64_ATOMIC_MIN_MAX`, есть
  не везде; запасной путь — две 32-битные записи). Делать только после основной части и замера:
  если треугольники в большинстве больше 4 px, выигрыш мал. Оценка: 8–10 дней, риск средний.
- Тесты: сравнение изображений аппаратной/программной растеризации на мелких треугольниках.

### 1.4 Материалы и шейдинг
- Visibility buffer → бининг пикселей по материалу → шейдинг (есть `vg_resolve.wgsl`). Нужно: корректная
  работа с будущим графом материалов (PLAN_MATERIALS.md): материал даёт функцию «поверхность по
  атрибутам вершин»; resolve-проход вызывает её для своей корзины.
- Вертексные атрибуты: позиции в квантованном виде (есть `compress.rs`), нормали, UV; тангенты
  вычисляются или хранятся по выбору материала.
- Оценка: 4–6 дней вместе с интеграцией в граф материалов (после этапа E).

### 1.5 Стриминг VG
- **Данные разбиваются на страницы** фиксированного размера (например, 64 КиБ), в страницу кладутся
  группы кластеров, которые нужны вместе. Корень иерархии (самый грубый уровень) **всегда резидентен**:
  поэтому «дыр» в картинке не бывает — при отсутствии детальной страницы рисуется родитель.
- **Запросы определяет GPU.** Проход выбора кластеров записывает в буфер «нужна страница N, но её нет»;
  CPU читает буфер с задержкой 1–2 кадра, ставит чтения из `.pak` (диапазонные чтения уже есть в
  `AssetSource::read_range`, приоритетная очередь есть), заливает в пул через staging-кольцо
  (`staging_ring.rs`), обновляет таблицу страниц.
- **Пул и вытеснение.** Пул страниц в видеопамяти с фиксированным бюджетом (МиБ). Вытеснение по давности
  использования (LRU, как у виртуальных теней); страницы, запрошенные в этом кадре, не вытесняются.
- **Кольцевой буфер.** Пул организован как кольцо/свободный список страниц, обновляется блоками в рамках
  бюджета на загрузку за кадр (как `upload_budget_bytes` у стримера текстур).
- **Сжатие.** Квантование (есть), позже — сжатие индексов/вершин (в духе meshoptimizer) и Zstd страниц
  в `.pak` для уменьшения диска.
- Тесты: GPU-тест прогрессивной загрузки (картинка сходится к полной), тест бюджета (память не
  превышает лимит при быстром пролёте камеры), тест вытеснения, повреждённая страница не роняет рендер.
- Оценка: 10–14 дней.

### 1.6 Что остаётся вне VG
Скиннинг, alpha-test, прозрачное и малые меши идут классическим путём (раздел 3). Решение, куда
отправить меш, принимается при импорте по порогам (число треугольников, материал, скиннинг) и
записывается в ассет.

## 2. HLOD (иерархический LOD мира)

- **Что это.** Не то же самое, что LOD внутри меша. HLOD заменяет **группу объектов** региона (дома улицы,
  камни на холме) одним упрощённым «прокси» на расстоянии, где отдельные объекты не различимы. Нужен
  для больших миров, где число объектов — главная нагрузка (draw calls, отсечение, память).
- **Сборка.** В `redox_cook` для каждой ячейки мира (см. `world.bin`, `partition.rs`) объединить
  статические меши ячейки, упростить, запечь текстуры (атлас альбедо/нормали) и положить прокси в мир.
  Несколько уровней: ячейка → блок ячеек → регион.
- **Рантайм.** Переключение по расстоянию с гистерезисом и перекрёстным затуханием (dither fade),
  стриминг ячеек по приоритету.
- **Связь с VG.** VG убирает нужду в LOD внутри меша; HLOD уменьшает **число экземпляров**. Они
  дополняют друг друга. Для объектов вне VG (классический путь) HLOD — основное средство.
- Тесты: сборка прокси детерминирована, переключение без «вспышек» (сравнение кадров до/после),
  память прокси меньше суммы исходных.
- Оценка: 8–10 дней.

## 3. Классический путь: инстансинг и indirect draw

- **Ваше понимание верно.** Меш хранится один раз; для экземпляров — массив данных (трансформ, предыдущий
  трансформ для скорости, индекс материала, цвет-вариация, флаги, границы). Один вызов
  `DrawIndexedInstanced` рисует все экземпляры; `Indirect`-версия берёт параметры из буфера, который
  заполняет сам GPU после отсечения. 5 000 вызовов превращаются в десятки.
- **Что сейчас.** Отдельный draw call на объект: процессор тратит время на подготовку и валидацию.
- **План по шагам.**
  1. **CPU-инстансинг.** Группировка видимых объектов по паре (меш, материал); один instance buffer на
     кадр; `draw_indexed(.., instance_range)`. Быстрый выигрыш. 3–4 дня.
  2. **GPU-сцена.** Постоянные буферы: экземпляры, таблица мешей, таблица материалов. Compute-проход
     отсечения (frustum + Hi-Z) пишет `DrawIndexedIndirect` в буфер; при поддержке — `multi_draw_indexed_
     indirect_count` (фича Vulkan), иначе по одному indirect на батч. 6–8 дней.
  3. **Bindless материалы.** Массив текстур (`TEXTURE_BINDING_ARRAY` + неоднородная индексация), чтобы
     не пересоздавать bind group на материал и сливать батчи. Нужна проверка поддержки на целевом GPU и
     запасной путь. 5–6 дней.
  4. **Единое хранилище per-object данных**, нужное также TAA (скорость динамических объектов) и теням.
- **Растительность.** Сильно выигрывает от инстансинга: ветер в вершинном шейдере, LOD по расстоянию
  (перекрёстное затухание), далёкие деревья — impostor'ы (билборды с запечёнными видами). См. PLAN_WORLD.md.
- Тесты: результат идентичен прежнему пути (golden-кадры), 10 000 экземпляров — время CPU-подготовки
  кадра падает в разы (замер до/после), корректность отсечения (ничего видимого не пропало).
- Итого: 3–4 недели.

## 4. GPU-скиннинг

- **Ваше описание верно.** Исходный меш с индексами костей и весами лежит в видеопамяти один раз; каждый
  кадр CPU отправляет только матрицы костей; GPU трансформирует вершины параллельно.
- **Как делаем (рекомендую).** Compute-проход «pre-skin»: читает исходные вершины и матрицы костей,
  пишет **деформированные вершины в общий буфер кадра**. Дальше все проходы (глубина, тени, основной,
  скорость) рисуют обычный меш из этого буфера. Плюсы: скиннинг один раз за кадр, а не в каждом проходе;
  легко хранить позиции прошлого кадра для **скорости** (нужна TAA); работает с VSM и другими проходами без
  изменений. Минус: дополнительная память под деформированные вершины (бюджет учитывается).
  Альтернатива «скиннинг в вершинном шейдере каждого прохода» проще, но считает всё по 3–4 раза.
- **Нормали и тангенты.** Ваше наблюдение верно: сейчас нормали при сгибах не следуют за костями (CPU-
  скиннинг двигает только позиции в пределах квантования). На GPU нормаль и тангент преобразуются той же
  взвешенной матрицей костей (линейная часть, при неравномерном масштабе — обратная транспонированная), затем
  нормализуются. Это даёт правильное освещение и нормал-мапы на сгибающихся мешах.
- **Данные:** буфер матриц костей на все экземпляры (смещение на экземпляр), буфер весов/индексов
  (4 влияния на вершину; 8 — опционально), буфер предыдущих позиций.
- **Границы.** Динамические границы меша для отсечения и инвалидации теней (сейчас `swept_bounds`): оставить
  консервативный расчёт по клипу/костям, не читая GPU назад.
- **Morph targets (blend shapes)** — следующей строкой после скиннинга (лицо, коррекции).
- Тесты: GPU-результат равен CPU-эталону (текущий код как эталон, допуск 1e-4), нормали при сгибе правильные,
  бенчмарк: 100 персонажей × 50 000 вершин — время CPU и GPU до/после; golden-кадры `skinned_demo`.
- Оценка: 6–8 дней (+ morph targets 3–4 дня).

## 5. Бюджеты памяти

- **Ваше понимание верно.** Жёсткие квоты по подсистемам, чтобы ничто не съедало всю память: например,
  текстуры N МиБ, пул VG M МиБ, страницы теней K МиБ, кэши GI и т.д. Внутри квоты подсистема сама решает,
  что держать: текстуры подгружают только нужный mip по близости (это уже делает `TextureStreamer`), VG —
  страницы кластеров по нужде и вытесняет старые.
- **Уточнение про физику и аудио.** Они живут в **оперативной памяти CPU**, а не в видеопамяти; у них свои
  лимиты (число тел, размер аудио-кэша), и «квота на физику» — это ограничение сущностей и кэшей, а не
  мегабайты видеопамяти.
- **Каркас (`MemoryBudget`).**
  1. Категории VRAM: `Textures`, `Geometry`, `Shadows`, `GlobalIllumination`, `RenderTargets`, `Staging`;
     категории RAM: `AssetCache`, `Physics`, `Audio`, `Scripts`.
  2. Учёт: все создания больших ресурсов проходят через обёртки, увеличивающие счётчики категории; отчёт в
     оверлее (есть место для этого в `redox_ui::debug`).
  3. Применение: каждая подсистема реализует трейт `Budgeted { fn used(&self) -> u64; fn target(&self) ->
     u64; fn shrink(&mut self, bytes: u64) -> u64 }`; менеджер раз в кадр сверяет суммарное потребление
     с общим лимитом и просит наименее приоритетные подсистемы сжаться.
  4. Уровни качества (Low / Medium / High / Ultra) задают квоты по умолчанию; пользователь может править.
  5. Определение объёма VRAM: wgpu его напрямую не сообщает; использовать значения уровня качества,
     настройку и (опционально) системный запрос через DXGI/Vulkan; по умолчанию — консервативно.
- Тесты: подсистема не выходит за квоту при стресс-сценарии; при уменьшении квоты память реально
  освобождается; оверлей показывает честные числа (сверка со счётчиками wgpu).
- Оценка: 5–7 дней каркас + подключение подсистем по мере появления.

## 6. Порядок и итог
GPU-скиннинг и CPU-инстансинг (быстрые победы) → GPU-сцена и indirect → каркас бюджетов →
иерархия кластеров → стриминг VG → HLOD → (опционально) программная растеризация. Итого 10–16 недель.
