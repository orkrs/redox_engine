Дата: 2026-10-17. Статус: реализовано (фазы 0–5, см. таблицу).

Все тесты затронутых крейтов (`redox_asset`, `redox_cook`, `redox_render`) зелёные на момент паузы.

Исходное состояние: `Ktx2Loader` читает KTX2 без суперсжатия, плоские 2D-текстуры с цепочкой mip
(`redox_asset/src/loader/ktx2_loader.rs`); `Texture::from_ktx2` грузит их на GPU
(`redox_render/src/resource/texture.rs`); материалы принимают KTX2 через `with_*_ktx2`;
`AssetManager` грузит в одном фоновом потоке, очередь без приоритетов, есть `set_completion_budget`.

## Что значит «в полной мере»

1. KTX2 с суперсжатием **Zstandard** и **Basis Universal** (ETC1S и UASTC) грузится и попадает на GPU
   в лучшем формате, который поддерживает устройство (BC7/BC3/BC1/BC5 или несжатый RGBA8).
2. **Кубмапы** и **массивы** текстур (6 граней, слои) грузятся и используются: окружение для IBL
   можно взять из готовых KTX2, а не только из equirect-картинки.
3. **Стриминг по приоритету**: ближние и важные текстуры грузятся раньше, сначала приходят
   маленькие mip, потом большие; есть бюджет памяти и выгрузка старших mip, когда память кончается.

Не входит: HDR-форматы ASTC/BC6H (отдельная задача), анимированные и 3D-текстуры, загрузка по сети.

## Принятые решения (с обоснованием)

| Вопрос | Решение | Почему |
|---|---|---|
| Распаковка Zstd | крейт `ruzstd` (чистый Rust) | не тянет C-сборку; скорость ниже `zstd` примерно в 1,5–3 раза, но распаковка идёт в фоновом потоке. Если замеры покажут узкое место, заменить на `zstd` за тем же интерфейсом |
| Транскодер Basis | крейт `basis-universal` (обёртка над C++ Binomial) | зрелого чисто-Rust транскодера нет; C++ собирается через `cc`, MSVC на Windows уже есть. Лицензия Apache-2.0 |
| Где транскодировать | в загрузчике на фоновом потоке, в формат, выбранный по возможностям устройства | главный поток не блокируется; формат известен до загрузки, если его передать загрузчику |
| Как загрузчик узнаёт формат | `Ktx2Loader::with_target(TranscodeTarget)`, приложение задаёт его один раз после создания устройства | у загрузчика нет доступа к `wgpu::Device` |
| Кубмапы в памяти | `Ktx2Texture { dimension, layers, faces, levels }`, данные уровня идут подряд: слой → грань | совпадает с раскладкой KTX2 |
| Стриминг mip | текстура создаётся сразу с полной цепочкой mip, сначала заполняются хвостовые (маленькие) уровни | материал сразу рисуется (размыто), чёткость приходит позже, без пересоздания bind group |
| Приоритет | число 0..=255 + пересчёт по расстоянию до камеры | простая модель, хорошо тестируется |

## Фаза 0. Подготовка и инструменты тестирования (0,5–1 день)

Цель: уметь получать тестовые KTX2 всех видов без внешних утилит.

- 0.1 Вынести построитель KTX2 из тестов `ktx2_loader.rs` в отдельный модуль `redox_asset::testing`
  (за `cfg(any(test, feature = "testing"))`): параметры формат, размер, число уровней, слои, грани,
  схема суперсжатия, данные SGD. Сейчас он дублируется в трёх местах.
- 0.2 Добавить dev-зависимость `zstd` (только для тестов, чтобы **сжимать** фикстуры) и `ruzstd` в основную.
- 0.3 Добавить в `redox_cook` подкоманду `texture-info <file.ktx2>`: печатает формат, размер, mip, слои, грани,
  схему суперсжатия (поможет диагностике дальше).
- 0.4 Определить матрицу проверки (см. «Проверка» внизу) и завести пустые тесты-заглушки с `#[ignore]`, которые
  каждая фаза включает.

Готово, когда: построитель фикстур покрыт тестами, `cargo test -p redox_asset` зелёный.

## Фаза 1. Суперсжатие Zstandard (1–1,5 дня)

Цель: файлы KTX2 со схемой Zstandard грузятся так же, как несжатые.

- 1.1 В `Ktx2Loader::load` заменить отказ на ветку: для схемы Zstandard каждый уровень распаковывается
  `ruzstd`; ожидаемый размер берётся из `uncompressedByteLength` индекса уровней и сверяется
  с `TextureFormat::level_size` (двойная проверка).
- 1.2 Защита от «бомб»: максимум распакованного размера на уровень (например 256 МиБ, настраивается),
  распаковка в буфер заранее известного размера, ошибка при несовпадении, ошибки без паник.
- 1.3 Схема BasisLZ (ETC1S) и неизвестные схемы остаются понятной ошибкой `UnsupportedFormat` до фазы 2.
- 1.4 Тесты: round-trip (сжатый и несжатый дают одинаковые байты), усечённый поток, поток с завышенным
  заявленным размером, пустой уровень, все форматы из `TextureFormat`.
- 1.5 Бенчмарк `ktx2_zstd_decode` (4096×4096 BC7): записать в `docs/BENCHMARKS.md`; порог для решения
  о замене `ruzstd` на `zstd`: больше 150 мс на такую текстуру.
- 1.6 `redox_cook texture-info` показывает схему и сжатый/распакованный размеры.

Готово, когда: фикстуры Zstd (все форматы, 1 и несколько mip) грузятся и проходят GPU-тест загрузки
(`ktx2_upload.rs`); fuzz-подобный цикл «каждый байт перевернуть» не паникует.

## Фаза 2. Basis Universal (2–3 дня)

Цель: файлы Basis (ETC1S через схему BasisLZ и UASTC) превращаются в формат, подходящий устройству.

- 2.1 Модель целей: `TranscodeTarget { Bc7, Bc3, Bc1, Bc5, Rgba8 }` в `redox_asset`; функция выбора по
  `wgpu::Features::TEXTURE_COMPRESSION_BC` и типу данных (цвет с альфой, цвет без альфы, двухканальная нормаль).
  Выбор живёт в `redox_render` (`TranscodeTarget::for_device(&device)`), загрузчику цель передаётся при
  регистрации: `mgr.register_loader::<Ktx2Texture, _>(Ktx2Loader::with_target(target))`.
- 2.2 Подключить `basis-universal` (с `default-features = false`, включить только транскодер, без энкодера в
  основной сборке; энкодер нужен только для `redox_cook`, см. 2.7). Проверить `cargo deny` (лицензии, advisories) и
  время сборки; зафиксировать результат в ADR 0004.
- 2.3 Разбор данных: для BasisLZ читать глобальные данные супер-сжатия (SGD: таблицы кодов, описания
  срезов), для UASTC (KTX2 с форматом `UNDEFINED` и дескриптором UASTC) читать блоки напрямую.
  Это самый рискованный шаг: на нём строится всё остальное, поэтому начинать с UASTC (проще),
  затем ETC1S.
- 2.4 Транскодирование по уровням в целевой формат; размеры уровней считаются по `level_size`
  целевого формата. Нечётные размеры: Basis работает блоками 4×4, внешний размер текстуры хранится
  отдельно (физический размер выровнен вверх) — учесть в `Texture::from_ktx2` (сейчас он отказывает
  для размеров не кратных 4: для транскодированных данных делать копию с обрезкой не нужно, достаточно
  создавать текстуру выровненного размера и выставлять UV-масштаб, либо отказ с понятной ошибкой;
  решение принять на этом шаге и записать).
- 2.5 Запасной путь: если BC недоступен, транскодировать в RGBA8 (память ×4–8, но работает везде).
- 2.6 Тесты: фикстуры UASTC и ETC1S создаются энкодером в тестовом коде из синтетической картинки
  (градиент + шахматка), после транскодирования в RGBA8 сравнивается PSNR с исходником (порог ≥ 30 дБ для
  UASTC, ≥ 24 дБ для ETC1S); GPU-тест загрузки результата для BC7 и RGBA8; тест «нет BC → RGBA8».
- 2.7 `redox_cook texture <in.png> <out.ktx2> [--uastc|--etc1s] [--normal] [--srgb] [--zstd]`: кодирует
  PNG/JPEG в KTX2 с mip. Энкодер подключается только в `redox_cook` (feature `encode`), чтобы игра
  не собирала его.
- 2.8 Пайплайн ассетов: `redox_cook pack` может принимать `.ktx2` как есть; опция `--textures` при
  упаковке перекодирует PNG→KTX2 (инкрементально через уже существующий stamp).

Готово, когда: один и тот же файл Basis загружается как BC7 на этом ПК и как RGBA8 при принудительном
отключении BC (тест подменяет цель); PSNR в допуске; сборка проходит `deny`, `clippy`, `doc`.

## Фаза 3. Кубмапы и массивы (1,5–2 дня)

Цель: кубическая текстура окружения грузится из KTX2 и используется рендерером.

- 3.1 Расширить `Ktx2Texture`: `layers: u32`, `faces: u32`, `dimension` (`D2`, `D2Array`, `Cube`, `CubeArray`).
  Загрузчик разрешает `face_count` 1 или 6, `layer_count` ≥ 0 (0 = одна текстура); `pixel_depth > 1` по-прежнему
  отказ. Проверка размера каждого уровня: `layers.max(1) × faces × level_size`.
- 3.2 Нарезка данных уровня на подресурсы в порядке KTX2 (слой, грань); для суперсжатия из фаз 1–2
  работает на уровне целого mip, затем нарезка.
- 3.3 `Texture::from_ktx2` создаёт `depth_or_array_layers = layers × faces`, заливает каждую грань и mip через
  `write_texture` с нужным `origin.z`; вид (`TextureViewDimension::Cube` / `CubeArray` / `D2Array`).
  Поле `Texture` получает `dimension`, чтобы привязка знала нужный layout.
- 3.4 Привязки: `SharedLayouts` уже имеет layout для 2D; добавить layout «cube» и функцию
  `create_cube_bind_group`. Материалы с массивами в этой фазе не обязательны (массивы нужны только как
  ресурс для будущих атласов), достаточно загрузки и теста.
- 3.5 IBL из готовых куб: `IBLResource::from_ktx2(environment, irradiance, prefiltered, brdf_lut)` —
  берёт уже запечённые KTX2 вместо вычисления на GPU. Существующий путь «equirect → куб → свёртки» остаётся.
- 3.6 `redox_cook bake-ibl <hdr_or_equirect> <outdir>`: запускает существующий GPU-конвейер `IBLProcessor`,
  читает результаты обратно и пишет три KTX2 (формат RGBA16F без сжатия; сжатие BC6H — отдельная задача).
  Это замыкает цикл «запечь один раз, грузить быстро».
- 3.7 Тесты: куб 6 граней разных цветов → читаем по граням шейдером-тестом или копированием обратно и
  сверяем; массив из 3 слоёв; ошибки: неверное число граней, неполные данные.

Готово, когда: пример `showcase` (или тест) стартует с IBL из KTX2, картинка совпадает с путём через
equirect в пределах допуска golden-сравнения (добавить отдельный golden-кадр).

## Фаза 4. Стриминг по приоритету (3–4 дня)

Цель: текстуры приходят в порядке важности, чёткость растёт постепенно, память ограничена.

### 4a. Очередь с приоритетами и отменой (0,5–1 день)
- 4a.1 Заменить `flume::unbounded` для задач на структуру «куча + Condvar» (`PriorityQueue`): порядок по
  (приоритет ↓, номер запроса ↑), чтобы одинаковые приоритеты шли по порядку запроса.
- 4a.2 API: `load_async_with_priority::<T>(path, Priority)`; `set_priority(handle, Priority)` меняет
  приоритет ещё не начатой задачи; `Priority` — тип-обёртка `u8` с константами `LOW`, `NORMAL`, `HIGH`, `URGENT`.
- 4a.3 Отмена: задача, чей актив выгружен (`release` до нуля) до начала чтения, выбрасывается воркером
  (проверка по общему `HashSet` живых id); сейчас результат только отбрасывается после загрузки.
- 4a.4 Несколько воркеров (по умолчанию `min(4, cpus-1)`), чтобы крупная распаковка не блокировала мелкие загрузки;
  порядок завершения не гарантируется, `completion_budget` по-прежнему ограничивает применение на кадр.
- 4a.5 Тесты: детерминированный порядок при одном воркере, перераспределение приоритета, отмена, отсутствие
  взаимных блокировок под нагрузкой (1000 задач, случайные приоритеты).

### 4b. Частичное чтение источников (0,5–1 день)
- 4b.1 `AssetSource::read_range(path, offset, len)` с реализацией по умолчанию через `read`, настоящие
  реализации для `DirSource` (seek) и `PakSource` (запись `.pak` с LZ4 читается целиком, для несжатых
  записей — диапазон). Для KTX2 в паке рекомендуется хранить без LZ4 (уже сжат Zstd/Basis): `redox_cook pack`
  по расширению `.ktx2` отключает LZ4.
- 4b.2 `Ktx2Header` и индекс уровней читаются первыми 4 КБ + индекс; хвостовые mip читаются диапазонами.
- 4b.3 Тесты: диапазоны на границах, за пределами файла, повреждённый индекс.

### 4c. Постепенная загрузка mip (1–1,5 дня)
- 4c.1 Новый тип ассета `StreamedTexture` (рядом с `Ktx2Texture`): сначала приходит «голова» — заголовок,
  формат, размеры, самые маленькие N mip (до 64×64); остальные уровни догружаются отдельными задачами.
- 4c.2 На стороне рендерера `Texture::streamed(device, head)` создаёт текстуру с полной цепочкой mip и
  заливает доступные уровни; `Texture::upload_level(queue, mip, data)` добавляет следующий. Минимальный
  допустимый mip задаётся `TextureViewDescriptor::base_mip_level` (пересоздание только вида; bind group
  пересобирается один раз при смене вида).
- 4c.3 Единая точка `TextureStreamer` (ресурс ECS): хранит для каждой текстуры текущий и желаемый mip, ставит
  в очередь догрузки с приоритетом и отдаёт рендереру готовые уровни не более `upload_budget_bytes` за кадр
  (используется существующий `StagingRing`).
- 4c.4 Тесты: порядок появления mip, отмена догрузки при выгрузке, бюджет байт за кадр соблюдается, GPU-тест
  чтения обратно того, что залито.

### 4d. Эвристика важности и бюджет памяти (1 день)
- 4d.1 Желаемый mip считается по экранному размеру объекта: `desired = log2(texel_size_on_screen⁻¹)`,
  по данным `RenderObject` (границы + расстояние до камеры) и размеру текстуры. Берём максимум по объектам,
  использующим текстуру; гистерезис (±1 mip), чтобы не дёргалось.
- 4d.2 Приоритет догрузки = f(желаемый − текущий mip, видимость в кадре). Невидимые получают `LOW`.
- 4d.3 Бюджет памяти (`texture_budget_bytes`): при превышении выгружаются старшие mip наименее нужных текстур
  (LRU по последнему кадру использования). Выгрузка = понижение `base_mip_level`, данные остаются
  в памяти GPU до пересоздания текстуры (честная оговорка: освобождение памяти требует пересоздания
  текстуры с меньшим числом mip, что делается пакетно раз в N кадров).
- 4d.4 Отладка: оверлей/лог `streaming: 312 textures, 1.4 GiB / 2.0 GiB, pending 12`, команда в
  палитру редактора.
- 4d.5 Тесты: синтетическая сцена из 200 текстур, камера летит; проверяем, что ближние достигают целевого mip
  раньше дальних, бюджет не превышается, нет мигания (число смен mip на текстуру за секунду ограничено).

Готово, когда: сцена с 200+ текстурами стартует и рисуется сразу (с размытыми текстурами), через
несколько секунд становится чёткой; пиковая память не выходит за бюджет; кадр не просаживается
(измеряется GPU-профайлером и бенчмарком загрузки).

## Риски

| Риск | Что делаем |
|---|---|
| `basis-universal` не собирается или тяжёлый по времени сборки | сначала фаза 1 и 3 (не зависят от него); Basis за feature `basis`, по умолчанию включён, но отключаем при проблемах |
| Раскладка SGD для ETC1S сложная | начинаем с UASTC, ETC1S вторым шагом; при блокировке ETC1S отложить, UASTC уже даёт качество и совместимость |
| Выгрузка mip не освобождает память GPU | пакетное пересоздание текстур; если вредит кадрам, ограничиваем только догрузкой (без выгрузки) и бюджетом на входе |
| Нечётные размеры BC | политика в 2.4: выровненная текстура + масштаб UV либо ясный отказ |
| Несколько воркеров ломают порядок событий | события применяются только в `update` на главном потоке; тесты порядка |

## Порядок и оценка

Фазы 0 → 1 → 3 → 2 → 4 → 5 (кубмапы раньше Basis: не зависят от внешней C++ библиотеки и дают видимый
результат). Стриминг (4) можно начинать параллельно с 2, он касается другой части кода.
Итого около 11–15 рабочих дней одним человеком; фазы независимо коммитятся и проверяются, после каждой
обновляется `PROGRESS.md`.
