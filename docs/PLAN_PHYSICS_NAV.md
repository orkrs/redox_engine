# План: физика и навигация

Общий контекст: [PLAN_TECH_OVERVIEW.md](PLAN_TECH_OVERVIEW.md). Код физики: `crates/redox_physics`
(обёртка над rapier3d 0.36: `RigidBody`, `Collider`, `Velocity`, `Kinematic`, `CharacterController`,
`Trigger`, лучи в `raycast.rs`/`context.rs`, синхронизация трансформов в `sync.rs`).

## Часть 1. Физика

### Что есть и чего не хватает

Есть: твёрдые тела и коллайдеры, kinematic character controller, триггеры (enter/exit), лучи с
нормалью и фильтром исключений. Нет: слоёв коллизий, шейп-кастов (sphere/capsule/box), overlap-запросов,
соединений (joints), ragdoll, событий контактов с импульсом, материалов физики как данных.

### 1.1 Слои коллизий

- **Что это.** Каждому коллайдеру назначается слой (кто я) и маска (с кем сталкиваюсь). Игрок не
  сталкивается со своими пулями, пули — с врагами и стенами, триггеры видят только игрока.
- **Это не «на основе ECS»**: слой хранится как компонент ECS (`CollisionLayers`), но сама фильтрация
  делается в rapier через `InteractionGroups` (две битовые маски: членство и фильтр). Компонент —
  удобный способ задать данные сущности; при создании коллайдера он переводится в `InteractionGroups`.
- **Как делаем.**
  1. Тип `Layer` — до 32 именованных слоёв; список имён и матрица взаимодействий в файле конфигурации
     (`physics_layers.ron`): `["Default", "Player", "Enemy", "Projectile", "Static", "Trigger", ...]` и
     таблица «слой × слой → сталкиваются/нет».
  2. Компонент `CollisionLayers { member_of: u32, collides_with: u32 }`, конструкторы по именам.
  3. При создании/обновлении `Collider` читаем компонент (по умолчанию слой Default, сталкивается со всеми).
  4. Все запросы (`raycast`, касты, overlap) принимают `QueryFilter { layers: u32, exclude: Option<Entity>,
     flags }`.
  5. Горячее изменение слоя у живой сущности: система `sync_layers` при изменении компонента.
- **Тесты.** Пуля игрока проходит сквозь игрока и попадает во врага; триггер реагирует только на слой
  Player; матрица читается из файла, ошибки формата дают понятное сообщение.
- **Готово, когда:** сценарий из трёх слоёв работает, запросы уважают фильтр, конфигурация
  проверяется при загрузке. **Оценка:** 2–3 дня.

### 1.2 Касты форм (sweep): sphere, capsule, box (и выпуклая форма)

- **Что это.** Как луч, но «толстый»: форма проезжает по направлению и возвращает первое столкновение
  (расстояние, точка, нормаль, сущность). Нужен для камеры от третьего лица, проверки «влезу ли в проём»,
  стрельбы толстыми снарядами, шагов персонажа.
- **API.**
  ```
  cast_shape(shape: Shape, pose: Transform, direction: Vec3, max_distance: f32, filter: QueryFilter)
      -> Option<ShapeHit { entity, distance, point, normal, started_penetrating: bool }>
  cast_shape_all(...) -> Vec<ShapeHit>   // все пересечения вдоль пути, по возрастанию расстояния
  Shape = Sphere(r) | Capsule(half_height, r) | Box(half_extents) | ConvexHull(handle)
  ```
- **Как.** Через `QueryPipeline::cast_shape` rapier; `Shape` переводится в `SharedShape`. Обработка
  случая «стартовое проникновение» (форма уже внутри коллайдера): флаг в результате, опция игнорировать.
- **Использование внутри движка.** Камера от третьего лица (отодвигаться при столкновении со стеной),
  `CharacterController` (проверка шага вперёд).
- **Тесты.** Капсула находит стену на правильном расстоянии; сфера проходит над порогом ниже её радиуса;
  стартовое проникновение; фильтры слоёв; сравнение с лучом при радиусе 0.
- **Оценка:** 2–3 дня вместе с overlap.

### 1.3 Overlap-запросы

- **Что это.** Да, вы поняли верно: «что находится внутри объёмной области». Форма ставится в точку, в
  результате все коллайдеры, которые её пересекают: взрыв (все в радиусе), зона аггро, проверка
  «свободно ли место для спавна».
- **API.**
  ```
  overlap_shape(shape, pose, filter) -> Vec<Entity>
  overlap_any(shape, pose, filter) -> bool          // быстрая проверка без списка
  overlap_point(point, filter) -> Vec<Entity>
  closest_point(entity, point) -> Option<ClosestPoint>   // расстояние до коллайдера
  ```
- **Как.** `QueryPipeline::intersections_with_shape` / `intersection_with_shape`. Версия с обратным
  вызовом, чтобы не выделять память на горячем пути.
- **Тесты.** Сфера радиуса 5 возвращает ровно те тела, что внутри; слои; пустая область.

### 1.4 Joints (соединения тел)

- **Что это.** Вы поняли верно с поправкой: один joint связывает **два** тела (или тело и мир). Цепь,
  дверь на петлях, мост, подвеска — несколько joints между парами тел.
- **Типы:**
  | Тип | Что делает | Пример |
  |---|---|---|
  | Fixed | жёстко склеивает | отломанная деталь, груз на платформе |
  | Revolute (hinge) | вращение вокруг одной оси, пределы угла, мотор | дверь, колесо |
  | Prismatic (slider) | скольжение вдоль оси, пределы, мотор | лифт, поршень |
  | Spherical (ball) | вращение вокруг точки в любую сторону, конус пределов | плечо ragdoll |
  | Spring | пружина с жёсткостью и демпфированием | подвеска |
  | Rope / distance | максимальная длина | верёвка, привязь |
  | Generic | свобода по выбранным осям | особые случаи |
- **Как.** ECS-компонент `Joint { other: Option<Entity>, kind, local_anchor_a, local_anchor_b, axis,
  limits, motor, break_force }` на сущности «A». Система `sync_joints` создаёт/удаляет joint в rapier при
  появлении/удалении компонента или тела, хранит соответствие `Entity → JointHandle`. Разрыв при превышении
  силы шлёт событие `JointBroken`.
- **Тесты.** Дверь на hinge качается и упирается в предел; fixed не расходится; цепь из 10 звеньев
  стабильна 10 секунд; удаление тела удаляет joint; разрыв по силе.
- **Оценка:** 4–5 дней.

### 1.5 Ragdoll и смешивание с анимацией

- **Что.** Скелет → набор тел и коллайдеров на костях, соединённых spherical/revolute joints с
  правдоподобными пределами. При смерти/ударе анимация отключается, позу ведёт физика.
- **Как.**
  1. Конфиг `RagdollDef` (какие кости, форма коллайдера — капсула, масса, пределы): генерируется по
     скелету автоматически, правится вручную.
  2. Включение: позу анимации копируем в тела (скорости из последних двух кадров анимации), включаем
     динамику; на каждый кадр позу костей берём из тел.
  3. Смешивание: «powered ragdoll» (моторы тянут к позе анимации) для реакции на удар, плавный возврат.
- **Тесты.** Падение ragdoll на пол без взрывов и проникновения, масса и пределы соблюдены.
- **Оценка:** 6–8 дней (после joints и GPU-скиннинга).

### Порядок физики
слои → касты и overlap → события контактов → joints → character controller 2.0 → ragdoll. Итого ~4–5 недель.

## Часть 2. Навигация

### Три разные вещи (чтобы не путать)
1. **Navmesh** — данные: сетка проходимых многоугольников. Её **запекают** (bake) из геометрии уровня.
2. **Поиск пути** — алгоритм (A* по полигонам + «натяжение нитки» funnel), даёт список точек маршрута.
3. **Избегание** — локальное поведение во время движения: обойти других агентов и динамические
   препятствия (ORCA/RVO). Не запекается, считается каждый кадр.

Так что запекание — лишь первая часть. Для динамических миров навмеш пересобирается **плитками**
(tiles) во время игры там, где что-то изменилось.

### 2.0 Исследование перед реализацией (обязательно по процессу)
Сравнить готовые крейты (например, реализации Recast на Rust, `polyanya`, `landmass`) по лицензии,
скорости, поддержке плиток и динамических препятствий; решить: взять готовый, обернуть или писать своё.
Результат — ADR 0007.

### 2.1 Запекание navmesh (в стиле Recast)
Шаги: вокселизация треугольников уровня в поле высот → отметка проходимых вокселей по высоте и углу
склона агента → построение регионов (watershed) → контуры → упрощение → полигональная сетка
(+ детальная высота). Параметры агента: радиус, высота, максимальный шаг, максимальный склон.
- Запуск офлайн в `redox_cook bake-navmesh` и в рантайме по плиткам (когда уровень стримится или
  изменился).
- Источники геометрии: статичные меши и коллайдеры, ландшафт (из PLAN_WORLD), отметка «не проходимо»,
  зоны с разной стоимостью (вода, грязь).
- Тесты: комната с проходом — сетка покрывает пол и не заходит в стены; лестница в пределах шага;
  препятствие разрывает покрытие; бит-в-бит повторяемость запекания.
- Оценка: 8–12 дней (меньше при использовании готового крейта).

### 2.2 Поиск пути
- A* по графу полигонов со стоимостями зон, затем funnel (string-pulling) для сглаживания.
- Запросы: `find_path(from, to, agent_class)`, `nearest_point`, `raycast_navmesh` (видимость по сетке),
  `random_point_in_radius`.
- Off-mesh связи: прыжок, дверь, лестница (ручные звенья графа с условием).
- Несколько классов агентов (малый/большой) → несколько сеток или параметры в плитках.
- Асинхронные запросы (на воркерах), кэш, лимит стоимости на кадр.
- Тесты: оптимальность на известных картах, отсутствие пути возвращает `None`, off-mesh работает.
- Оценка: 5–7 дней.

### 2.3 Избегание столкновений
- Локальное управление толпой: ORCA/RVO2 (скорость выбирается так, чтобы не пересечься с соседями),
  плюс разделение и «прилипание» к навмешу.
- Динамические препятствия: вырезание из плиток (carving) и временные запреты, перепланирование.
- Интеграция с `CharacterController` и физикой (агент не проходит сквозь стены).
- Тесты: два агента навстречу обходят друг друга; толпа 200 агентов идёт к цели без застреваний;
  время обновления < 1 мс на 200 агентов.
- Оценка: 5–6 дней.

### 2.4 ECS и API
Компоненты `NavAgent { class, radius, height, speed, accel }`, `NavTarget(Vec3)`, `NavPath`; ресурс
`NavMesh`; события `PathReached`, `PathFailed`. Хост-API для WASM: `nav_path`, `nav_set_target`.
Debug-отрисовка сетки и путей. Оценка: 3 дня.

### Порядок навигации
исследование → запекание → поиск пути → ECS/отладка → избегание. Итого 3–5 недель; не зависит от
рендера, можно делать в любой момент после слоёв и кастов физики.
