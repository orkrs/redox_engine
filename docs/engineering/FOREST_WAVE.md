## 3. Правило «одного писателя рендерера»

В `redox_render` одновременно меняет код ровно один агент: файлы `renderer/*`, `pbr.wgsl`, `material_surface.wgsl`, `frame_graph.rs`, `material.rs`, `matgraph_passes.rs`, `pass/*`. Остальные агенты могут читать, добавлять новые файлы и тесты и править другие крейты. Если агенту нужна правка в занятых файлах, он описывает её в отчёте, а не вносит.

## 4. Общие правила исполнителя (копируются в промпт)

- **Модель: haiku.** Один шаг спеки за один заход. Не расширяй объём.
- **Среда.** Работа в своём worktree: `git merge --ff-only main`, затем скопировать `Cargo.lock` из `main`. Сборки всех агентов идут в общий каталог целей и стоят в очереди, поэтому не запускай лишних.
- **Что можно запускать.** `cargo fmt`; `cargo check -p <крейт> --all-targets`; свои новые тесты по одному бинарю (`cargo test -p redox_render --test <имя>`); GPU-тесты в отдельных бинарях, до 8 рендереров на файл (иначе утечка видеопамяти и «Out of Memory»). **Не запускай:** `cargo clippy` по рабочему пространству, `cargo test --workspace`, замеры производительности (кроме явно записанных в спеке), `git push`.
- **Git.** Коммитить в ветку своего worktree **только по явным путям** (`git add <файл> …`). Запрещены `git add -A`, `git add .`, `git add crates`. Никогда не добавлять: `assets/forest/` (сотни МБ, не в git), `crates/redox_core/examples/rus_universalis/`, `RedOx_Editor_Full_Spec.md`. Сообщение коммита: `<тип>: <описание>` (feat, fix, test, docs, perf) и строка `Co-Authored-By: Claude Haiku 4.5 <noreply@anthropic.com>`.
- **Слово «ПРОВЕРИТЬ» в спеке** означает, что факт не подтверждён чтением: проверь его до работы и запиши результат в отчёт; если он расходится со спекой, остановись и опиши расхождение.
- **Кадры без новых флагов побитно прежние.** Любой шаг, который меняет существующие кадры, считается ошибкой, пока не доказано обратное.
- **Лимит попыток.** Одна основная попытка плюс одна доработка по списку замечаний координатора. Если приёмочный тест красный после доработки, остановись, запиши измеренное число или сообщение об ошибке и верни отчёт; исход назначает координатор.
- **Отчёт.** Файл `docs/engineering/notes/<ID>-report.md`: что сделано (шаги, файлы), что проверено (команды и вывод одной строкой), числа замеров, что не получилось и почему, что координатору проверить. Без слов «примерно работает».
- **Стиль кода.** Как в окружающем коде: комментарии по плотности как рядом, имена как рядом; файлы ≤ 800 строк (`python scripts/check_file_sizes.py`), без `unwrap()` в библиотечном коде, `missing_docs` в публичном API.

## 5. Что делает координатор

- Пишет и правит спеки; выдаёт агенту ровно один шаг с готовым промптом (шаблон ниже).
- После каждого шага проверяет сам, а не по отчёту: `cargo fmt`, `cargo clippy --workspace --lib --bins --tests -- -D warnings`, нужные GPU-тесты по одному, `check_file_sizes.py`, `gen_crates_doc.py --check` (если менялись крейты), diff на лишние файлы.
- Сливает ветку агента (`git merge`), решает конфликты, прогоняет замеры из спеки, обновляет `BENCHMARKS.md`.
- Принимает решения по воротам: FOL-01 шаг 3 по числу (≤ 6 мс CPU на 10 000 объектов), SKY-02 после SKY-01, MAT-08 шаг 5 после INV-01, FOL-03 после FOL-01.
- Коммит и итоговый push только после того, как раунды закрыты и полный прогон зелёный; явное слово владельца нужно на push.

## 6. Шаблон промпта для агента

```
Ты исполнитель задачи <ID> проекта RedOx (Rust, wgpu 30, Windows). Модель: haiku.
Спека: docs/engineering/specs/<ID>.md. Общие правила: docs/engineering/FOREST_WAVE.md §4.
Выполни ТОЛЬКО шаг <N> спеки. Не расширяй объём.

Контекст: <1–2 предложения: зачем шаг и что уже сделано/решено координатором>.
Подготовка: git merge --ff-only main; скопируй Cargo.lock из main.
Что сдать: <файлы/тесты из спеки>; отчёт docs/engineering/notes/<ID>-report.md.
Приёмка: <тесты шага по именам>. Запускай только cargo fmt, cargo check -p <крейт> --all-targets и свои тесты по одному.
Правила: один шаг за заход; коммит только по явным путям; не трогай assets/forest, examples/rus_universalis, RedOx_Editor_Full_Spec.md; не пушь.
Если приёмочный тест красный после одной доработки — остановись и опиши числа.
Советы: <конкретные подсказки к шагу: какие файлы читать первыми, типичные ловушки>.
```

Подсказки по ловушкам для типовых шагов:
- **GPU-тесты:** один рендерер на тест ограниченно, отдельные бинарии; свет в кадре задаётся `DirectionalLight::direction` как вектор **к** солнцу; камера в тестах `camera_uniform.update(&camera, pos, rot)` затем `update_camera_buffer()`.
- **Формат кадра для чтения:** `read_texture_ktx2(&device, &queue, &target, false)`, цель `Rgba8Unorm` с `COPY_SRC`.
- **Новые устройства:** фичи берутся из `adapter.features() & wanted`; `INDIRECT_FIRST_INSTANCE` уже в списке.
- **Heredoc в оболочке:** тексты с апострофами и обратными слэшами писать инструментом Write, а не `<<EOF`.

## 7. Риски

| Риск | Что делаем |
|---|---|
| Haiku не доводит шейдерную математику (SKY-02 шаги 1–2, FOL-03 шаги 2–3) | эталон на CPU и тест сходимости в каждом шаге; две попытки агента, затем координатор; исход 📌 с числом |
| Конфликты в `renderer/*` | правило §3; перенос правок в окно писателя |
| Сборки в общем каталоге целей стоят в очереди | один `cargo check` за заход, без лишних тестов |
| GPU-тесты падают из-за памяти или соседних процессов | отдельные бинари, ≤ 8 рендереров на файл, перезапуск одиночно |
| Расследование не находит причину | допустимый исход: 📌 с перечнем исключённого и числами |
| Правка меняет существующие кадры | обязательные тесты «побитно прежний» в каждой спеке |
