# EDT-A7 — Редактор, этап A, срез A7: сценарные тесты этапа A (приёмка по ТЗ §23)

- **Статус:** не начат.
- **Размер:** 5 шагов (M, M, M, S, S) ≈ 5 дней. **Крейты:** `redox_editor` (тесты), `redox_editor_core`, `redox_editor_scene`, `redox_editor_assets`, `redox_editor_debugger`. **Зависит от:** EDT-A1…A6 (вместе). **Блокирует:** закрытие этапа A; B1…B8.
- **Исполнение:** агент (haiku) без cargo; координатор запускает прогон сценариев и замеры. Шаги 1–2 строят каркас и данные, шаги 3–4 сценарии.
- Источник: `EDITOR_PLAN.md` §5 A7, §11; ТЗ §23 (пункты 1, 2, 3, 5, 6, 12, 13, 14, 18 и часть 8, 16).
- **Не входит:** GUI-тесты (скриншоты viewport идут в B3), CI на GitHub (C4), нагрузочные пороги как условие приёмки (в A7 числа только фиксируются).

## Суть
Каждый срез A1–A6 проверяется своими модульными тестами, но этап A считается закрытым, когда работают сквозные сценарии из ТЗ §23. Срез собирает одну тестовую «ручку» редактора без окна и GPU, учебный проект-образец и сценарии, которые проверяют именно пользовательские обещания: сохранил и открыл, отменил, переименовал, сломал импорт, «упал» и восстановился, открыл проект с битыми ссылками.

## Шаг 1 — тестовая ручка `EditorHarness` и каркас (M)
- Модуль `redox_editor/tests/common/mod.rs` (подключается сценариями): `EditorHarness { ctx: EditorContext, project: Option<ProjectContext>, level: Option<Level>, assets: Option<AssetService>, autosave: AutosaveService, clock: TestClock, root: TempDir }`.
- Методы: `new_project(template)`, `open_project(path)`, `restart()` (создаёт новую ручку на тех же файлах, как перезапуск процесса: сбрасывает память, оставляет диск), `crash()` (как `restart`, но **без** штатного закрытия: оставляет `session.lock` и автосохранения), `run(command_id)`, `save()`, `advance_clock(secs)`, `snapshot()` (снимок мира), `tick()` (автосохранение, сервис ассетов), `write_file(path, bytes)`, `touch_asset(path)`.
- `TempDir`: свой временный каталог без внешних зависимостей (`std::env::temp_dir()` + уникальное имя, удаление в `Drop`).
- Построители данных: `make_png(w, h)`, `make_glb(triangle)` (минимальный GLB), `make_scene(entities)`, `corrupt(path)`.
- Тест на каркас: `a_harness_restarts_on_the_same_files`.

## Шаг 2 — проект-образец и фикстуры (M)
- `crates/redox_editor/tests/data/sample_project/`: `project.ron`, `scenes/main.scene.ron` (камера, свет, пять объектов с иерархией из трёх уровней, ссылки на два ассета), `assets/textures/checker.png` (малый PNG), `assets/models/triangle.glb` (минимальный GLB).
- Версия образца хранится **в репозитории как данные**, а не собирается кодом, чтобы изменение формата ловилось тестом чтения старого файла (`the_sample_project_opens_without_warnings`).
- Вторая фикстура `sample_project_broken/`: ссылка на отсутствующий файл ассета, неизвестный компонент в сцене, плагин в `project.ron`, повреждённый `.meta` у одного ассета.
- Генерация образца описывается в `crates/redox_editor/tests/data/README.md` (как обновить при смене формата: открыть редактором, сохранить, закоммитить).

## Шаг 3 — сценарии A (M)
Файлы `redox_editor/tests/scenarios/*.rs`, один сценарий на файл или группу; каждый ссылается на пункт ТЗ §23.

| Файл | Сценарий | ТЗ |
|---|---|---|
| `s01_project_roundtrip.rs` | создать проект из шаблона `3d_starter`, `restart`, открыть, стартовая сцена та же, `recent` содержит проект | §23.1 |
| `s02_scene_roundtrip.rs` | создать сцену с несколькими объектами, компонентами, камерой и светом, сохранить, `restart`, открыть, снимок мира и GUID равны; повторное сохранение даёт те же байты | §23.2 |
| `s03_edit_undo.rs` | переместить, переименовать, дублировать, удалить и сменить родителя; Undo/Redo всех шагов возвращает снимки; иерархия и GUID целы; dirty по таблице A3 | §23.3 |
| `s05_asset_rename.rs` | переименовать и переместить ассет в проекте с двумя сценами (открытой и закрытой), все ссылки остаются целыми после `restart` | §23.5 |
| `s06_references.rs` | найти зависимые сцены ассета, удаление без `force` предупреждает, с `force` ссылки становятся `MissingAsset` и не пропадают | §23.6 |
| `s12_import_failure.rs` | три файла в очереди, один повреждён: `Failed` у одного, `Imported` у остальных, исходник цел, редактор продолжает работать; повтор после исправления | §23.12 |
| `s13_crash_recovery.rs` | изменить сцену, `advance_clock` до автосохранения, `crash`, открыть, `RecoveryOffer` есть, принять: состояние равно автосохранению и dirty; отказ переносит файлы в `discarded/` | §23.13 |
| `s14_broken_project.rs` | открыть `sample_project_broken`: редактор не падает, отчёт содержит `MissingAsset`, `UnknownComponent` (значение сохранено), `MissingPlugin`, `damaged` `.meta`, проект открывается | §23.14 |

## Жёсткие правила исполнителя (без исключений)

Эти два правила важнее любых других строк спеки и промпта. Нарушение любого из них считается невыполнением задачи.

1. **Делай ВСЕ поставленные задачи и шаги до конца, без исключений.** Не пропускай шаги, не откладывай их «на потом», не останавливайся на полпути и не сдавай частично («остальное позже» не принимается). Если шаг неоднозначен, выбери вариант, который прямо назван в спеке (или самый простой из совместимых со спекой), запиши выбор одной строкой в отчёт и **продолжай**. Каждая строка раздела «Что сдать» и каждый тест из списка должны быть реализованы в коде. Единственное допустимое «не сделано»: шаг, который спека сама помечает как условный (с названием условия); в отчёте перечисли его и условие.
2. **АБСОЛЮТНО НИКАКИХ ПРОГОНОВ. Ничего не запускай.** Запрещено любое выполнение кода проекта и инструментов сборки: `cargo` (build, check, test, run, clippy, bench, doc, fmt), `rustc`, `rustfmt`, запуск тестов, бенчмарков и примеров, запуск собранных программ и редактора, любые замеры, скрипты, которые собирают или выполняют проект. Разрешено только: читать файлы, искать по ним, править и создавать файлы, `git` (add по явным путям, commit, status, diff, log). Компиляцию, форматирование, тесты, замеры и ручные проверки выполняет координатор по твоему отчёту. Поэтому пиши код и тесты **полностью и аккуратно с первого раза**: перечитывай собственные правки, сверяй имена и сигнатуры с исходниками, проверяй типы и заимствования глазами. Если для проверки чего-то обычно понадобился бы прогон, напиши это в отчёте списком «координатору проверить» (точные команды и что ожидается), но сам не запускай.

## Риски
| Риск | Что делаем |
|---|---|
| Ручка тестов дублирует логику приложения и расходится с ним | Ручка вызывает те же команды и сервисы (`run(command_id)`), собственной логики не содержит; расхождения ловит ручной дым-тест |
| Тесты на файловой системе нестабильны на Windows (блокировки) | Уникальные каталоги, повтор удаления в `Drop`, отсутствие внешних наблюдателей в тестах, где они не нужны |
| Сценарии медленные из-за очереди импорта и наблюдателя | Таймауты сценариев по `TestClock`, ожидание событий по счётчикам, а не по `sleep` |
| Образец устареет при смене формата | README данных и тест `the_sample_project_opens_without_warnings` падают первыми и подсказывают, что обновить |
