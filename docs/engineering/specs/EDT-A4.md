# EDT-A4 — Редактор, этап A, срез A4: autosave и восстановление после аварии

- **Статус:** не начат.
- **Размер:** 4 шага (M, M, S, S) ≈ 4 дня. **Крейты:** `redox_editor_core`, `redox_editor_scene`, `redox_editor_ui`, `redox_editor`. **Зависит от:** EDT-A2 (сериализация сцены), EDT-A3 (`is_dirty`). **Блокирует:** A7 (сценарий «авария»).
- **Исполнение:** агент (haiku) без cargo; координатор компилирует и тестирует после шагов.
- Источник: `EDITOR_PLAN.md` §5 A4; ТЗ §1.4, §2.1, §23.13.
- **Не входит:** синхронизация между пользователями, облачные копии, восстановление PIE-сессии, автосохранение настроек редактора (кроме проверки атомарной записи layout).

## Суть
Сейчас при аварии редактора несохранённая работа теряется: autosave нет, `TimeTravelBuffer` хранит снимки только в памяти, а `write_atomic` оставляет лишь копию `.bak` последнего сохранения. Срез добавляет автосохранение в отдельный каталог проекта (оригинальный файл автосохранением не трогается), признак «сессия активна», предложение восстановления при следующем запуске и проверку, что остальные файлы редактора пишутся безопасно.

## Что уже есть (проверено чтением кода)
- `redox_scene::ofpa::write_atomic`: `*.tmp.<pid>` → копия в `*.bak` → `rename`; используется для OFPA и (после A2) для сцены.
- `redox_editor_debugger::TimeTravelBuffer` (кольцо снимков в памяти) и `PieSession` — к восстановлению после аварии отношения не имеют.
- `editor_layout.ron` пишется через `EditorDock::save_to_file` (**ПРОВЕРИТЬ**, атомарна ли запись); при ошибке разбора `load_from_string` сохраняет текущий layout (частичный safe-layout).
- После A2: `SceneDocument` с детерминированной сериализацией, `LoadReport`; после A3: `UndoStack::is_dirty()`.

## Шаг 1 — служба автосохранения (M)
- `redox_editor_core::autosave::AutosaveService` с политикой `AutosavePolicy { interval_secs: u32 (120), every_n_transactions: u32 (25), keep: usize (3), enabled: bool }`; время подменяемо (`trait Clock`) для тестов.
- Хранилище внутри проекта: `<project>/.redox/autosave/<имя-уровня>.<n>.scene.ron` (кольцо из `keep` файлов, номера по возрастанию) плюс `<project>/.redox/session.lock`.
- Вызов `tick(&EditorContext, &Level)` из главного цикла: срабатывает, если уровень `dirty` и выполнено условие интервала или числа транзакций; делает снимок на главном потоке (клонирование `WorldSnapshot`), запись выполняет фоновый поток (`flume`-канал) **во временный файл и `rename`**; оригинальный файл уровня не затрагивается.
- Для `Level::World` (OFPA) автосохранение пишет только список изменённых актёров в `<project>/.redox/autosave/<мир>/<cell>/<id>.ron`; восстановление для мира в A4 ограничено предложением (см. шаг 2), полная ручка для OFPA помечается 📌 в отчёте, если усложняет срез.
- Тесты (без GPU, с подменёнными часами и синхронным режимом записи): не dirty → автосохранения нет; dirty и интервал истёк → один файл; пять срабатываний → хранится `keep` последних, номера растут; содержимое автосохранения при загрузке даёт тот же снимок, что и мир; оригинальный `*.scene.ron` после автосохранения побайтово не изменился.

## Шаг 2 — блокировка сессии и предложение восстановления (M)
- `session.lock` (RON): `pid`, `started`, `project`, `level`, `heartbeat` (время). Обновление `heartbeat` каждые 5 секунд тем же `tick`. При штатном закрытии (в том числе после решения «сохранить» или «не сохранять») файл удаляется вместе с автосохранениями этого уровня.
- При открытии проекта: если `session.lock` существует и его `heartbeat` старше `2 × interval_secs`, но не менее 30 секунд (сессия считается аварийной; проверка живости процесса по pid не используется, чтобы не вводить `unsafe` и новые зависимости), и в `autosave/` есть файл новее уровня, формируется `RecoveryOffer { level, autosave_path, autosave_time, level_time }`.
- Принятие: уровень загружается из автосохранения и отмечается изменённым, **исходный путь сохраняется** (Save запишет в оригинал после подтверждения); отказ: автосохранения переносятся в `.redox/autosave/discarded/<время>/`, не удаляются до следующего успешного сохранения.
- Повреждённое автосохранение (не разбирается): предложение не показывается, предупреждение в журнал, файл переносится в `discarded/`, редактор открывается нормально.
- Если блокировка свежая (< порога), открытие проекта показывает «проект уже открыт другой сессией» и позволяет продолжить **только** по явному подтверждению.
- Тесты: оставленная блокировка со старым `heartbeat` и автосохранением новее уровня → `RecoveryOffer`; принятие даёт состояние автосохранения и dirty; отказ переносит файлы в `discarded/` и удаляет блокировку; штатное закрытие удаляет блокировку и автосохранения; свежая блокировка → отказ без подтверждения; повреждённое автосохранение не создаёт предложения и не падает.

## Шаг 3 — безопасная запись остальных файлов (S)
- Аудит записей редактора: `editor_layout.ron`, `editor_recent.ron`, `project.ron`, файлы сцены, автосохранения. Все идут через общую функцию `redox_scene::write_atomic` (или её копию с тем же поведением, если зависимость нежелательна); разрозненные `std::fs::write` в редакторе заменяются.
- Тест-страж `redox_editor/tests/atomic_writes.rs` в духе `undo_discipline`: запрещает `std::fs::write(`/`File::create(` в `redox_editor*/src` вне списка (логи, тесты, временные каталоги).
- Layout: повреждённый `editor_layout.ron` (не разбирается) → редактор открывается с layout по умолчанию, ошибка в журнале, повреждённый файл переименовывается в `editor_layout.ron.broken` (ТЗ §2.1).
- Тесты: повреждённый layout → дефолтный layout и файл `.broken`; страж зелёный.

## Шаг 4 — UI (S)
- Диалог восстановления при открытии проекта (Recover / Discard / Cancel) с временем автосохранения и временем файла.
- Статусная строка: «Autosaved HH:MM» после записи; «Recovered from autosave» после восстановления.
- Параметры автосохранения (`enabled`, интервал) в одном месте `EditorSettings` (минимальная структура в `redox_editor_core`, RON `editor_settings.ron`, запись атомарная); отдельной панели настроек в A4 нет, меню `Edit → Preferences` открывает простое окно с этими тремя полями.
- Ручной дым-тест (координатор): изменить сцену, подождать автосохранение, принудительно завершить процесс, запустить и принять восстановление.

## Риски
| Риск | Что делаем |
|---|---|
| Отсутствие проверки живости процесса даёт ложные «аварии» | Порог по `heartbeat` и явное подтверждение при свежей блокировке; живость процесса оставить на будущее с отдельной зависимостью |
| Запись в фоне гоняется с закрытием окна | При закрытии `AutosaveService::flush()` дожидается очереди (с таймаутом 2 с), тест на закрытие во время записи |
| Автосохранение крупного мира замедляет UI | Снимок клонируется на главном потоке только для сцен; для OFPA пишутся только изменённые актёры; замер на 10 000 сущностей в A7 |
| Windows блокирует переименование открытого файла | Повтор `rename` до 3 раз с паузой 50 мс; ошибка в журнал, автосохранение пропускается до следующего цикла |
