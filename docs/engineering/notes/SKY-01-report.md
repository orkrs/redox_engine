## Критерии «причина найдена»
- **A:** синтетика. Ожидание по конвенции файла: «+Y 60°» и «−Z 60° вверх» → синий (небо); «−Y 60°» и «−Z 60° вниз» → зелёный. Если синее оказывается внизу, а зелёное вверху — вертикальный флип (см. гипотезу A1). Горизонталь: в −Z (forward) должен быть белый, +X → красный, +Z → пурпурный, −X → жёлтый. Если цвета сдвинуты на 90° — горизонтальный поворот конвенции (A2), это не флип и не «стена холмов».
- **A, HDRI:** сравнить среднее по строкам файла (8 полос; полоса 0 = верх файла) с цветом кадра на +60° и −60°. Если верх файла — тёмная земля/холмы, а кадр +60° даёт такой же цвет — флип подтверждён (вариант i). Если верх файла голубой и +60° тоже голубой, источник не виноват, а «стена холмов» — свойство HDRI (вариант ii).
- **B:** `ratio = light/shadow` при `sun_scatter = 1`. Порог принятия фикса — ratio ≥ 1,5 (тест `assert`). Ожидание до фикса по гипотезе B1: ratio ≈ 1,0–1,1 (это совпадает с «≤ 1,1» из спеки).

## Гипотезы по чтению кода (не проверены замером)

### A1 — вертикальный флип equirect (вероятная причина)
- `crates/redox_render/shaders/equirect_to_cube.wgsl:24`: `return vec2<f32>(phi / (2.0 * PI) + 0.5, theta / PI + 0.5);`
- Строка 23: `theta = asin(v.y)`. Верх картинки (строка 0 файла, v = 0) соответствует θ = −π/2, то есть y = −1 (низ). Итог: верх файла показывается внизу, и наоборот.
- Грузчик `Texture::from_hdr_bytes` (`src/resource/texture.rs:361`) строк не переворачивает (`into_rgb32f`, без flip), поэтому строка 0 — это верх файла.
- Кандидатное исправление (одна строка, но файл вне моих разрешённых путей для fog; equirect_to_cube.wgsl в списке разрешённых): `theta / PI + 0.5` → `0.5 - theta / PI`. **Не применено**: корень подтвердится только замером синтетики (`synthetic_equirect_seen_from_each_direction`). Если замер покажет флип — применить и добавить `equirect_axes_match_the_convention` по образцу тестов из `sky_probe.rs`.
- Кубовая часть проверена чтением и согласована с соглашением GPU по всем шести граням (`get_cube_dir`, строки 9–19): ошибок в гранях нет.

### A2 — горизонтальный сдвиг на 90° (наблюдение, не баг по умолчанию)
- `phi = atan2(v.z, v.x)` (строка 22): центр карты (u = 0,5) соответствует +X, тогда как в принятой панорамной конвенции центр — это −Z. Сравнение: u_conv(d) = u_std(d) − 0,25 (проверено на +X, +Z, −Z, −X).
- Зеркала нет: направление u растёт от −Z к +X, как и должно.
- Это вопрос выбора конвенции для всех HDRI и `skybox.hdr`. Решение за координатором; в этом заходе не меняю.

### B1 — знак направления солнца в фазовой функции (главная гипотеза по B)
- Сам `LightUniform::dir_direction` хранит направление **к** солнцу: `DirectionalLight::new(direction)` (`src/light.rs`, `direction` = вектор к солнцу, подтверждается тестом mat07 «towards the light»); `pbr.wgsl:1044` использует его как `l` (к свету); `src/renderer/frame/gi.rs:17` явно берёт `sun_dir = -dir_direction` (то есть «куда светит солнце»).
- `src/post/post_fx.rs:187` и `src/renderer/frame/post.rs:143` передают `dir_direction` как `sun_direction` (как будто это «куда светит»). В `src/post/fog.rs:119–122` (`fog_uniform`) значение копируется без инверсии, а поле в униформе (`fog.rs:99`, `fog_inject.wgsl`, `fog.wgsl`) задокументировано как «direction the sun shines in».
- Фаза: `shaders/fog_inject.wgsl:198` и `shaders/fog.wgsl:100`: `hg_phase(dot(ray, -fog.sun_dir.xyz), g)`. Из-за двойной инверсии `cos = dot(ray, от солнца)`. При взгляде на солнце (ray = к солнцу) `cos = −1`, `hg` минимален. Для g = 0,5: `phase(cos = +1) ≈ 0,477`, `phase(cos = −1) ≈ 0,018` — различие ≈ 27 раз; при этом пик туман получает, глядя **в противоположную** сторону.
- Прямое следствие: света в зазорах почти не видно, ratio ≈ 1 (соответствует спеке). Это же поведение у аналитического `fog.wgsl`.
- **Кандидатное исправление (не применено, так как не замерено):** в `src/post/fog.rs` `fog_uniform`, строки 119–122: отрицать направление солнца, то есть `unit_or_zero([-frame.sun_direction[0], -frame.sun_direction[1], -frame.sun_direction[2]])`. Это одна строка в разрешённом файле и меняет только кадры с `sun_scatter > 0` (члены `scatter.x * sun_color * phase` при `sun_scatter = 0` обнуляются точно: кадры с `sun_scatter = 0` побитно прежние). Затрагивает и аналитический туман (`fog.wgsl`) при `sun_scatter > 0`. Порог фикса: ratio(ss=1) ≥ 1,5. Вариант «поменять знак в `fog_inject.wgsl:198`» тоже работает, но расходится с документацией поля униформы; предпочтительнее `fog.rs`.

### B2 — прочие пункты списка спеки (исключены чтением, не замером)
- Размер сетки: `FROXEL_W/H/D = 160/90/64` (`fog_inject.wgsl:53–55`; `fog_froxel.rs:12–17`), `FROXEL_MAX_DISTANCE = 120 м` (`fog_inject.wgsl:57`, `fog_froxel.rs:23`). Сетка по глубине экспоненциальная (`slice_depth`, `fog_inject.wgsl`): с far = 25 м первый срез ≈ 0,1 м, ячейка у 24 м ≈ 2,4 м (ratio по срезам ≈ (25/0,1)^(1/64) ≈ 1,09 на срез). Для тонких колонн 0,5 м это грубо, но спец-тест даёт ширину колонны ~10 px и сетка по x/y — 160×90 на кадре 256 px: ~1,6 px на froxel — колонны видны, но тени по x размыты на одну-две froxel. **Не главная причина** при ratio ≈ 1.
- VSM: `sun_visibility` (`fog_inject.wgsl`) возвращает 1 при `level_count == 0` или при отсутствии страницы; **промахи страниц не измерены** (счётчик не добавлен, так как нельзя запускать). Если ratio после B1-фикса < 1,5, следующая проверка — счётчик промахов `vsm_lookup`.
- Экспозиция/bloom и временное накопление: в тесте не отключены (`enable_taa(false)`, как в `tests/fog_froxel.rs`). Открытый вопрос: комментарий в `fog_froxel.rs` и `renderer/settings.rs:204` говорит, что туман работает только при TAA, а существующий тест вызывает `enable_taa(false)`. Координатору проверить, что туман виден (`froxel_fog_pulls_distant_pixels_towards_the_fog_colour` проходит).
- `sun_dir` и `sun_color` в униформе берутся только из `LightScene` (`post.rs:143–144`); отдельного источника в `FogSettings` нет (сверено).
