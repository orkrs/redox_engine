# План редактора RedOx Studio: от текущего состояния к production-среде

Дата: 2026-11-05. Основание: целевое ТЗ `RedOx_Editor_Full_Spec.md` (в корне репозитория, пока не в git; далее «ТЗ») и аудит кода редактора на коммите `4feb336`. Это **план**, а не ТЗ: здесь есть сверка с кодом, срезы работы, приёмка, оценки и порядок.

Как читать: §1 коротко о выводах; §2 что уже есть (по коду); §3 решения, которые нужны от владельца; §4 правила плана; §5–§7 срезы по этапам A, B, C; §8 что отложено и при каких условиях; §9 тесты и агенты; §10 риски; §11 приёмка.

Важное ограничение аудита: код редактора прочитан, **сам редактор не запускался**. Статус «есть» означает «в коде есть реализация», а не «проверено в работе».

## 1. Выводы

1. Редактор уже существует: три крейта (`redox_editor` 2,2 тыс. строк, `redox_editor_core` 3,9 тыс., `redox_editor_ui` 2,9 тыс.), egui + egui_dock, общее устройство и Renderer с движком. Это не «с нуля», как следует из ТЗ.
2. Есть сильные заготовки: Undo/Redo через reflect-снимки, PIE с восстановлением мира, GUID-реестр ассетов с `.meta`, OFPA с атомарной записью, `HotReloadWatcher`, `redox_cook` с набором команд, git-трекер по актёрам, GPU-пикинг по ID-буферу, гизмо, кисть.
3. Главный разрыв не в количестве панелей, а в **фундаменте этапа A из ТЗ**: нет Save/Load сцены в редакторе (Ctrl+S сохраняет только layout), нет manifest проекта, нет autosave и восстановления после аварии, нет метаданных свойств в reflect, реестр ассетов не подключён к редактору, нет транзакций с группировкой.
4. Viewport рисует прокси-кубы и землю; Virtual Geometry, GI и SDF в редакторе не подключены, IBL заглушка, режимы Unlit/Normals/Wireframe не реализованы (по комментарию в `render_host.rs`). То есть редактор не показывает то, чем сильнее всего отличается движок.
5. Порядок этапов A → B → C из ТЗ верный. Но ТЗ нужно нарезать на **вертикальные срезы с автоматической приёмкой**: каждый срез даёт сквозную возможность («открыл → изменил → отменил → сохранил → закрыл → открыл») и проверяется тестом без GUI.
6. Чтобы тесты были возможны без GUI, первым делом нужен **headless `EditorContext`** (срез A1): сейчас состояние редактора живёт в `EditorApp` внутри окна.

## 3. Принятые решения (владелец, 2026-11-05)

Формат мира OFPA (папка с файлами объектов и ячейками) **сохраняется для больших миров** и открывается редактором как второй вид уровня | A2 делает один файл основным путём и главным результатом; OFPA-мир остаётся как есть и не переписывается; общий слой `Level` скрывает разницу |
| D2 | Раскладка крейтов редактора | **Сразу разложить по ТЗ на много крейтов**, продолжая раскладку остального проекта | Новый срез A1 включает раскладку (§3.1) |
| D3 | UI-инструментарий | **egui + egui_dock остаются** | Без изменений |
| D4 | Формат проекта | **`project.ron`**: версия формата, версия движка, стартовая сцена, корень ассетов, активные плагины, профили сборки | A2 |

### 3.1 Раскладка крейтов (D2)

Принцип: **выше по списку зависит от ниже**; крейты без egui тестируются без окна; цикла между UI и runtime нет. Бинарь `redox_editor` остаётся приложением (роль `redox_editor_app` из ТЗ); переименовывать его не нужно, это лишний шум в истории.

| Крейт | Роль | Что переезжает или появляется |
|---|---|---|
| `redox_editor` (бинарь) | окно, меню, главный цикл, привязка событий | остаётся, `app.rs` становится тонким слоем над контекстом |
| `redox_editor_ui` | общие виджеты, панели, dock, палитра | остаётся (egui здесь и только здесь, кроме бинаря) |
| `redox_editor_core` | `EditorContext`, команды, Undo и транзакции, выбор, проект и манифест, autosave, логи, настройки редактора | остаётся, получает контекст (A1) |
| `redox_editor_scene` | уровни (`SceneLevel`, `WorldLevel`), иерархия и модель Outliner, валидация сцены | `world_session.rs` переезжает из core; новые модули по срезам A2, B1, B7 |
| `redox_editor_assets` | интеграция `AssetRegistry`, очередь импорта, миниатюры, зависимости и аудит | пустой скелет в A1, наполняется в A6, B4, C2 |
| `redox_editor_viewport` | камера, гизмо, пикинг, проходы viewport, overlays, кисть | `camera.rs`, `gizmo.rs`, `picker.rs`, `viewport/*`, `viewport_mode.rs`, `brush.rs` переезжают из core |
| `redox_editor_debugger` | PIE, time travel, профилировщик, консоль, runtime-инспектор | `pie.rs`, `time_travel.rs`, `profiler.rs` переезжают из core; новые модули в B6, C3 |
| `redox_editor_build` | профили сборки, cook, упаковка | логика из `PackagerPanel` (bake, экспорт пакета) отделяется от UI; наполняется в C1 |
| `redox_editor_plugins` | манифест плагина и типы API | только скелет (D6), загрузчик в C6 |

Правило зависимостей: `redox_editor` → `redox_editor_ui` → { `scene`, `assets`, `viewport`, `debugger`, `build`, `plugins` } → `redox_editor_core` → крейты движка. Крейты `scene`, `assets`, `debugger`, `build`, `plugins` не зависят от egui; `viewport` зависит от wgpu, но не от egui.

## 4. Правила плана

- **Срез**: законченная сквозная возможность, а не слой. Каждый срез имеет цель, список файлов, тесты приёмки (желательно headless) и оценку.
- **Спека на срез**: перед работой по срезу пишется короткая спека `docs/engineering/specs/EDT-<этап><номер>.md` по образцу существующих (шаги, границы, проверка, закрытие ✅/⛔/📌). Спеки пишет координатор.
- **Один писатель на файл**: на `redox_editor_core/src/undo.rs`, `redox_reflect/src/lib.rs`, `redox_editor/src/app.rs` одновременно работает один агент.
- **Ничего не ломать**: существующие тесты крейтов `redox_editor_core`, `redox_editor_ui`, `redox_reflect`, `redox_scene` остаются зелёными на каждом шаге.
- **Оценки** в агент-днях (работа одного исполнителя с проверкой координатора), грубые. Календарь зависит от параллелизма и лимитов.
- **Агенты**: haiku, один шаг за заход, без права запускать cargo (тесты и замеры у координатора), коммит только по явным путям; подробности `FOREST_WAVE.md` §4.

## 5. Этап A: фундамент (срезы A1–A7)

Цель этапа (из ТЗ): закрыл редактор и открыл без потери сцены; Undo/Redo работает для core-действий; переименование ассета не ломает ссылки; сбой импорта не валит приложение; после аварии восстанавливается autosave.

Порядок: A1 → A2 → A3 → (A4, A5 параллельно) → A6 → A7. A1 блокирует остальные: без headless-контекста их нельзя проверять автоматически.

### A1. Раскладка крейтов, headless `EditorContext` и граница editor/runtime (≈6 дней)

- **Зачем:** разложить редактор по крейтам (D2) и вынести состояние и логику из `EditorApp` в тестируемый сервис без egui и окна.
- **Что сделать:** `EditorContext` в `redox_editor_core` (мир, `TypeRegistry`, `UndoStack`, `Selection`, `PieSession`, `WorldSession`/`Level`, логи, очередь событий). `EditorApp` становится тонким слоем: берёт события окна, вызывает контекст, рисует. Команды редактора переходят на единый интерфейс `Command::execute(&mut EditorContext)` с идентификаторами (задел для палитры и горячих клавиш). Явно пометить editor-only данные (компонент-маркер `EditorOnly`).
- **Раскладка крейтов (§3.1):** создать `redox_editor_scene`, `redox_editor_assets`, `redox_editor_viewport`, `redox_editor_debugger`, `redox_editor_build`, `redox_editor_plugins`; перенести существующие модули (список в §3.1) без изменения поведения; обновить `Cargo.toml` рабочего пространства, зависимости и `docs/CRATES.md` (`scripts/gen_crates_doc.py`). Крейты без наполнения (`assets`, `build`, `plugins`) получают скелет: описание в `lib.rs`, `#![warn(missing_docs)]`, один тип-заглушка с тестом, чтобы крейт собирался и не был пустым.
- **Где:** новые крейты и `Cargo.toml`; `redox_editor_core/src/context.rs` (новый), `redox_editor/src/app.rs`, `app/redraw.rs`, `commands.rs`.
- **Тесты:** контекст создаётся без GPU и окна; в нём можно выполнить «создать сущность → изменить свойство → Undo → Redo» (проверка равенства снимков мира). Проверки раскладки: `cargo tree` у крейтов `core`, `scene`, `assets`, `debugger`, `build`, `plugins` не содержит `egui`; цикла зависимостей нет; все существующие тесты перенесённых модулей зелёные.
- **Риск:** перенос модулей и рефакторинг `EditorApp` меняют много строк; сначала переносить без изменений (отдельным коммитом), потом вводить контекст; существующие хоткеи и палитру не менять. Один агент на весь срез, параллельных правок в `core` и `app.rs` в это время нет.

### A2. Проект и сцена-документ: Save/Open/Save As с безопасной записью (≈6 дней)

- **Зачем:** без сохранения сцены редактор не редактор (ТЗ §3, §4.2, §20).
- **Что сделать:**
  1. `project.ron` (D4) и `ProjectContext`: открыть/создать проект, шаблон «пустой» и «3D starter», резервная копия перед миграцией, версия формата.
  2. `Level` (D1): **`SceneLevel` один файл `*.scene.ron` это основной путь**; `WorldLevel` (OFPA) остаётся для больших миров и открывается как второй вид уровня; загрузка и запись OFPA не переписываются.
  3. Стабильные ID: компонент `EntityGuid(u128)` у каждой сущности сцены, назначается при создании; ссылки между сущностями по GUID, а не по индексам.
  4. Save, Save As, Open, закрытие с вопросом о несохранённом; dirty-флаг в заголовке; запись через `write_atomic` (уже есть в `redox_scene::ofpa`).
  5. Ctrl+S сохраняет документ, layout сохраняется отдельным пунктом.
- **Где:** `redox_editor_core/src/project.rs`, `redox_editor_scene/src/level.rs`, `redox_scene` (формат сцены и версия), `redox_editor/src/app.rs` и меню.
- **Тесты (headless):** roundtrip «собрать сцену → сохранить → загрузить → снимки равны»; порядок и GUID стабильны между сохранениями; повреждённый файл даёт диагностическую ошибку, предыдущая версия остаётся (атомарная запись); миграция со старой версией создаёт резервную копию.
- **Приёмка из ТЗ §23:** пункты 1 и 2.

### A3. Транзакции и расширение Undo (≈4 дня)

- **Зачем:** ТЗ §0.2.1: любое изменение данных проходит через команды.
- **Что сделать:** `UndoStack::begin_transaction(name)` / `commit` / `cancel` с вложением; новые команды `Reparent`, `Rename`, `SetAssetRef`, `MoveAsset` (после A6), `AddComponent`/`RemoveComponent`; журнал операций с именами (панель «Undo History»); `dirty` вычисляется по позиции в стеке относительно точки сохранения. Аудит: все точки изменения мира в `redox_editor*` идут через стек (поиск прямых `world.insert/despawn`, кисть и гизмо оформляются транзакциями одним шагом).
- **Где:** `redox_editor_core/src/undo.rs`, `brush.rs`, `gizmo.rs`, панели UI.
- **Тесты:** вложенные транзакции откатываются одной операцией; Undo после Redo даёт исходный снимок; операция кисти одной транзакцией (ТЗ §4.5); dirty сбрасывается после сохранения и возвращается после Undo.
- **Приёмка из ТЗ §23:** пункт 3.

### A4. Autosave и восстановление после аварии (≈2 дня)

- **Что сделать:** autosave в служебную папку проекта по таймеру и после N транзакций; файл блокировки «сессия активна»; при старте, если блокировка осталась, предложить восстановление; ротация копий.
- **Где:** `redox_editor_core/src/autosave.rs`, `app.rs`.
- **Тесты:** «аварийное завершение» имитируется оставленной блокировкой и autosave-файлом: контекст предлагает восстановление и после принятия состояние равно последнему autosave; нормальное закрытие удаляет блокировку.
- **Приёмка из ТЗ §23:** пункт 13.

### A5. Метаданные свойств в reflect и переработка Inspector (≈5 дней)

- **Зачем:** ТЗ §1.3 и §5; сейчас `ReflectField` знает только имя и тип.
- **Что сделать:** расширить `ReflectField`: `category`, `tooltip`, `range`, `step`, `unit`, `default`, `read_only`, `hidden`, `advanced`, `editor_only`; атрибуты в `redox_reflect_derive` (`#[reflect(range = 0.0..=1.0, tooltip = "...")]`); `ReflectValue` для ссылок на ассеты хранит GUID (после A6) и ожидаемый тип; Inspector: категории, поиск, reset, mixed value при мультивыборе, редактор по типу значения, предупреждение о несовместимой ссылке. Миграции версий компонентов (минимальный механизм `migrate(from_version)`).
- **Где:** `redox_reflect`, `redox_reflect_derive`, `redox_editor_ui/src/inspector.rs`, регистрация существующих компонентов.
- **Тесты:** derive выдаёт метаданные; значение вне диапазона отклоняется или приводится по правилу; мультивыбор с разными значениями показывает mixed и Undo возвращает все.
- **Риск:** `ReflectSchema` используется в сохранении; изменения должны быть обратно совместимыми.

### A6. Реестр ассетов в редакторе: ссылки по GUID, перемещение, очередь импорта (≈6 дней)

- **Зачем:** ТЗ §6.2, главный пункт «переименование не ломает ссылки».
- **Что сделать:**
  1. Подключить `AssetRegistry` к `EditorContext`; браузер работает по GUID, а не по путям.
  2. Ссылки на ассеты в компонентах хранятся как GUID (A5); путь вычисляется через реестр.
  3. Перемещение/переименование/удаление ассета из редактора идёт через реестр и команды Undo; удаление показывает список ссылающихся сущностей (поиск обратных ссылок по сценам проекта).
  4. Файловый наблюдатель `HotReloadWatcher` переводится на инкрементальное обновление реестра; команда Rescan/Repair.
  5. Очередь импорта в фоне: состояния Importing/Imported/Failed/Outdated, прогресс, отмена, повтор; **падение одной задачи не влияет на остальные**; ошибка показывается панелью со ссылкой на источник.
- **Где:** `redox_asset` (статусы, обратные ссылки, потокобезопасное обновление), `redox_editor_core/src/assets.rs`, `redox_editor_ui/src/asset_browser.rs`.
- **Тесты:** переименование и перемещение файла оставляет ссылки целыми (сцена загружается и ссылка разрешается); удаление ассета предупреждает о ссылках; источник с ошибкой импорта даёт статус Failed, остальные ассеты импортируются, редактор жив; дубликат GUID при копировании файла с `.meta` получает новый GUID (это в реестре уже есть, проверить в редакторе).
- **Приёмка из ТЗ §23:** пункты 4, 5, 6, 12.

Один тестовый sample-проект в `crates/redox_editor_core/tests/data/`.

## 6. Этап B: ежедневный workflow (срезы B1–B8)

Начинать после A2 и A3. Срезы B3 и B5 самые большие; B3 зависит от движка.

### B1. Outliner и иерархия (≈5 дней)
Иерархия с родителем (`Parent`/`Children` через reflect), reparent с Undo и сохранением мирового/локального трансформа, группы-папки, мультивыбор (диапазон, дети, инверсия), hide/lock/isolate, поиск и фильтры (имя, компонент, ошибка), виртуализация списка. **Тесты:** reparent сохраняет мировой трансформ; Undo возвращает дерево; фильтр находит по компоненту; 50 000 сущностей не строят дерево целиком (замер времени кадра UI на заранее заданном размере).

### B2. Компоненты и массовое редактирование (≈3 дня)
Добавить/удалить/скопировать компонент, поиск по категориям (метаданные A5), предупреждения о зависимостях, копирование значений между сущностями, мультиредактирование, Reset. **Тесты:** добавление зависимого компонента предупреждает; копия значений одной транзакцией.

### B3. Viewport, который показывает движок (≈8 дней)
Реальные меши и материалы вместо прокси-кубов (после AST-01 шаг 3 и MAT-08), режимы Lit/Unlit/Wireframe/Normals/Roughness/Depth, небо и IBL (после SKY-02), VG-экземпляры, переключатели GI/SDF/тумана, ортографические виды, snapping (сетка, поверхность, вершина), скриншот, FPS/GPU-время (только реально измеряемое; неподдерживаемое помечается). **Зависит от движка:** волна лесной сцены (мост glTF, двусторонние материалы, небо). **Тесты:** golden-скриншот viewport на контролируемой сцене (допуск 3/255); режим Wireframe отличается от Lit по заданному критерию.

### B4. Импорт моделей и текстур из редактора (≈5 дней)
Диалог импорта, preview, пресеты по типам, reimport при изменении источника, миниатюры в фоне с кэшем (меш на нейтральном фоне), журнал импорта. Опирается на AST-01 шаги 3–5 и A6. **Тесты:** reimport после изменения source сохраняет пользовательские настройки; миниатюра строится асинхронно, UI не блокируется (замер).

### B5. Редактор материалов (≈8 дней)
Открытие `.matgraph`, граф узлов на `NodeCanvas` с типами пинов, компиляция через `redox_matgraph` и пайплайны движка, ошибки с переходом к узлу, превью на сфере/кубе/плоскости с выбором освещения, параметры и инстансы материала, вывод сгенерированного WGSL, горячая перезагрузка (механизм в `matgraph_cache.rs` уже есть). **Правило из ТЗ:** материал, который не собирается для игры, сохранить нельзя. **Тесты:** граф с ошибкой типов не сохраняется и показывает узел; корректный граф даёт ожидаемый цвет на превью (GPU-тест как `mat03_tex_gpu`).

### B6. PIE и отладка (≈4 дня)
Step one frame, выбор стартовой сцены и аргументов, запуск Standalone отдельным процессом, защита от записи persistent данных во время Play, консоль с уровнями, категориями, фильтрами, переходом к объекту, экспортом; runtime inspector (поиск по ID и имени, подсветка выбранного). **Тесты:** после Stop мир равен снимку до Play (уже частично есть, расширить на иерархию и ссылки); step выполняет ровно один кадр.

### B7. Валидация сцены и отчёт об отсутствующих ссылках (≈3 дня)
Правила: отсутствующий ассет/компонент, материал с ошибкой, нет стартовой камеры, объект вне границ, цикл вложений, тяжёлые текстуры без mip. Панель с severity, источником и действиями Fix/Select/Open. **Тесты:** каждая правило срабатывает на минимальной сцене-фикстуре; Fix устраняет.

### B8. CLI проекта (≈3 дня)
`redox_cook validate <project>`, `import`, запуск sample-проекта без GUI, отчёты JSON. **Тесты:** `validate` на sample-проекте даёт 0 ошибок, на фикстуре с битой ссылкой ненулевой код выхода и отчёт.

**Итого этап B:** ≈39 агент-дней (диапазон 32–50). Приёмка по ТЗ §23: пункты 7, 8, 14, 15, 16.

- **Этап A закрыт**, когда проходят автоматически: создание проекта и повторное открытие; сохранение и загрузка сцены с одинаковым результатом; Undo/Redo всех типов команд; переименование и перемещение ассета без потери ссылок; поиск ссылок и предупреждение при удалении; сбой импорта не валит редактор; восстановление после аварии; открытие проекта с отсутствующим ассетом даёт отчёт (ТЗ §23: 1, 2, 3, 5, 6, 12, 13, 14).
- **Этап B закрыт**, когда небольшую 3D-игру (несколько сцен, материалы, свет, физика, ввод) можно собрать без ручного редактирования внутренних файлов (ТЗ §23: 7, 8, 15, 16; DoD этапа B).
- **Этап C закрыт**, когда CI открывает проект, проверяет ссылки, импортирует, собирает и тестирует без GUI, регрессии видны в отчёте (ТЗ DoD этапа C).
